# Proposal: WI-094 Scoping — Capability & Cash Meta-Orchestrator Decomposition

**Filed:** 2026-04-25
**Author:** Claude Opus 4.7 (on behalf of svc framework)
**Status:** APPROVED-FOR-PROMOTION — ready for capture-idea --from-proposal
**Source WI:** WI-094 (Capability & Cash Meta-Orchestrator, severity:high)

## Why this proposal exists

WI-094 is the largest and highest-leverage item in the current backlog: severity:high, framework lane, explicitly flagged by the builder as "the reason I can't break out of 'great framework, no revenue'." Its scope as filed spans persistent state (capability registry), cross-project read-only visibility, three distinct recommendation lenses, a cash-reinvestment doctrine, capability re-discovery, and an honest diagnosis output. That's at least 6 distinct subsystems packed into one WI.

Shipping all of it as a single changeset would:

1. Require one of the largest specs in the repo.
2. Risk partial delivery (the "great framework, no revenue" pattern the WI is meant to break).
3. Collide with existing adjacent skills (`mine-builder`, `find-opportunity`, `manage-finops`, `roadmap-evaluation`, `assess-market-readiness`) without a clean integration story.

Per the scoping directive: decompose WI-094 into 5 bounded children, each independently shippable.

## Decomposition principles applied

- **Each child WI is independently shippable.** No child depends on a sibling except through artifacts on disk.
- **Lowest-risk / highest-leverage first.** A machine-readable capability registry unlocks every downstream lens; author that first.
- **Adjacent skills are extended, not duplicated.** Where an existing skill already does 80% of the work (`mine-builder`, `find-opportunity`), the child WI extends it rather than spawning a new skill.
- **No continuous-running daemon in v1.** The orchestrator runs on explicit invocation; "continuous" is a later evolution once the on-demand version is proven.

## Phased Plan

### Phase 1 — Capability & Cash Meta-Orchestrator Child WIs

Five bounded child WIs decomposed from WI-094. Sequencing: P1.1 → P1.2 → P1.3 → P1.5 → P1.4. Shipping P1.1 through P1.3 delivers ~80% of the value.

#### Acceptance Criteria (phase-level)

- **AC-phase-1:** Each child WI emitted has its own goal, acceptance criterion, and scope boundary. No child is a stub.
- **AC-phase-2:** Children cite the parent WI-094 in their Source field for traceability.

##### P1.1 — Capability Registry (foundation)

**Type:** feature
**Severity:** high
**Lane:** framework

**Goal:** produce `~/.svc/capabilities/registry.json` — a persistent, per-builder inventory of paid + free AI/dev resources, separate sub-budgets, quotas, reset cadence, last-verified date, and host mapping.

**Acceptance Criteria:**
- `node scripts/capability-registry.mjs list` enumerates ≥7 resources from the illustrative inventory in WI-094 (GPT Business, Claude Max ×5, Kimi, Gemini Pro, MiMo, Base44, Namecheap).
- Each entry carries separate-budget capabilities as nested fields (e.g. GPT Business → Codex CLI + Deep Research as separate meters).
- Registry survives across sessions (on disk under `~/.svc/capabilities/`).
- Schema validated by a tier-1 script `validate-capability-registry.sh`.

**Scope boundary:** pure state + CRUD. No recommendations, no cross-project reads, no auto-discovery. One JSON file + one validator + one SKILL.md for updating it.

**Size estimate:** small-medium, ~1 day.

**Blocks:** P1.2, P1.3, P1.4, P1.5.

##### P1.2 — Cross-Project State Reader (visibility)

**Type:** feature
**Severity:** medium
**Lane:** framework

**Goal:** produce a read-only aggregator that scans a configured list of project roots (`~/.svc/projects.json`) and extracts each project's `docs/specs/project-state.md`, work-item INDEX, last-N learnings, and FRAMEWORK-STATE.md. Emits a compact cross-project snapshot at `~/.svc/state-snapshot.json`.

**Acceptance Criteria:**
- Given 3 fake project dirs with mixed states, the aggregator emits a single snapshot listing: per-project active WI count, blocked-on-what, time-since-last-commit, and a framework row.
- Read-only across project boundaries — no mutation (validated by a tier-1 check grepping for write operations outside the svc repo).
- Aggregation time under 2s for 10 project roots.

**Scope boundary:** data extraction only. No advice, no ranking, no recommendations. The snapshot is the deliverable.

**Size estimate:** small-medium, ~1 day.

**Blocked by:** P1.1.
**Blocks:** P1.3, P1.5.

##### P1.3 — Recommendation Lenses (the brain)

**Type:** feature
**Severity:** high
**Lane:** framework

**Goal:** implement the three lenses as an on-demand skill `capability-concierge`:
1. Ship-the-current-project lens — smallest move to push the highest-priority unfinished project toward first revenue. Invokes `roadmap-evaluation` and `assess-market-readiness` under the hood.
2. Idle-resource lens — which resources in the registry are under-used this reset window vs capacity.
3. Side-earning lens — invoke `find-opportunity` filtered by the capabilities the builder actually holds.

Output is a single ranked list: recommendation + lens + rationale + required resource + acceptance test if executed.

**Acceptance Criteria:**
- Invoking `capability-concierge` on a fixture (registry + cross-project snapshot + mocked reset windows) produces exactly one ranked recommendation per lens (3 recs) with evidence-graded rationale.
- Every recommendation cites the registry entry + snapshot row it came from.
- No hallucinated capabilities — if a recommendation references a resource not in the registry, the skill fails with an explicit error.

**Scope boundary:** runs on existing state. Does not maintain state. Does not do auto-discovery. Reinvestment doctrine is a configurable parameter here, not a separate WI.

**Size estimate:** medium-large, ~2 days.

**Blocked by:** P1.1, P1.2.

##### P1.4 — Capability Rediscovery (keep registry fresh)

**Type:** feature
**Severity:** low
**Lane:** framework

**Goal:** periodic re-check of vendor pages / changelogs for new separate-budget capabilities. Flags stale entries in the registry (last-verified-date > 30 days) and proposes updates based on web search + vendor docs. Uses the refactored `research` skill (WI-090 pre-scope + fallback + domain gate).

**Acceptance Criteria:**
- Invoking rediscovery on a registry entry older than 30 days produces a diff proposal at `~/.svc/capabilities/pending-updates/<resource>.md` with cited sources.
- Builder reviews and accepts via a one-line accept command.
- No silent auto-updates — human checkpoint before any registry write.

**Scope boundary:** discovery + proposal only. No auto-apply.

**Size estimate:** small-medium, ~1 day.

**Blocked by:** P1.1.

##### P1.5 — Honest Diagnosis (the "why haven't I shipped" answer)

**Type:** feature
**Severity:** high
**Lane:** framework

**Goal:** on-demand skill that answers the builder's load-bearing question: "why have I not shipped a revenue product despite owning this framework?" Produces an evidence-graded blocker report citing: resources under-deployed, projects half-finished, behaviors visible in `pipeline-decisions.jsonl` (e.g. skill-hopping, premature-completion, unused credits).

**Acceptance Criteria:**
- Given P1.1 + P1.2 outputs + the session-level `pipeline-decisions.jsonl`, the diagnosis names ≥3 concrete blockers with evidence paths.
- No platitudes — every blocker anchored to a file path + line or a decision-log entry.
- If the diagnosis is ambiguous, it says "I cannot distinguish X from Y without more data" rather than fabricating confidence.

**Scope boundary:** diagnostic only. Proposes at most the smallest sequence of 3 moves the ship-lens (P1.3) would recommend. No auto-execution.

**Size estimate:** medium, ~1-1.5 days.

**Blocked by:** P1.1, P1.2, P1.3.

## Cross-cutting decisions deferred

- **Continuous / daemon mode.** All 5 children are on-demand. A future WI can layer a scheduled invocation (cron, pre-prompt hook) once the on-demand variants prove useful.
- **Cash-reinvestment threshold.** P1.3 exposes this as a config knob; choosing the actual threshold is a builder decision, not a framework decision.
- **Skill vs extension of existing skill.** P1.3 names a new skill (`capability-concierge`) but P1.5 may fold into `assess-market-readiness` or `roadmap-evaluation` depending on how their evidence-grading contracts align. That decision belongs in `validate-feature`, not here.
