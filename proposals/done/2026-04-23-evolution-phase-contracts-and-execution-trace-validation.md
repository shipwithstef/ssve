## Findings (by priority)

### P0 — Skills promise processes they never prove they execute

**Evidence:** `diagnose-bug/SKILL.md` declares 10 process tasks (Step 0 through Step 5.5.2), 3 flags (`--diagnose-only`, `--retroactive`, `--progressive`), 20 self-verify checks, and a pillar revisit audit. **None of these internal paths are tested.** `test-framework/evals/tier-2/scenarios/diagnose-bug-typo.md:30-42` asserts only output artifacts (file exists, typo named, root cause mentioned). It does NOT verify:
- Step 0.3 bug-domain classification was performed
- Step 0.35 SKIP comment grep happened
- Step 0.4 pre-lock rejection ran
- Step 2 pattern scan across related modules was attempted
- Step 4.4 pillar revisit audit walked all 8 pillars
- Self-verify table was actually checked before completion
- Task graph was updated with `STATUS: READY_FOR_PLAN`

**Impact:** A skill can produce a plausible-looking brief while skipping every internal quality gate. The tier-2 test passes, the tier-3 judge scores 10/10/10, but the skill cheated. This is AP-26 (skill substitution) at the **sub-skill level** — the agent substituted the full process with a template-completion shortcut.

**This already happened.** The 10/10/10 tier-3 score on `diagnose-bug-typo` was achieved via an injected prompt template, not by `diagnose-bug/SKILL.md` alone. The skill's internal process was bypassed; the output was generated by a compressed prompt. FRAMEWORK-STATE.md:66-89 documents this but does not classify it as a testing failure.

**Fix:** Every skill must declare Execution Phases in its contract, and tier-2 must validate execution traces against those declarations.

### P0 — Tier-3 coverage is 1/35 scenarios (2.8%), giving false confidence

**Evidence:** FRAMEWORK-STATE.md:22 says "**tier-3 judge operational** (completeness/actionability/consistency scoring via kimi --print --yolo -p)" — but does not note that only ONE scenario (`diagnose-bug-typo`) has been judged. The 10/10/10 score is treated as a framework win without acknowledging it covers 0.04% of the scenario surface (1 of ~2,240 possible skill-flag-fixture combinations).

**Impact:** The framework claims tier-3 is operational. A user reading FRAMEWORK-STATE.md would reasonably conclude quality gating exists. In reality, 97.2% of tier-2 scenarios have never been judged. A skill could regress across 34 scenarios and the framework would not detect it.

**Fix:** Add tier-3 coverage metrics to FRAMEWORK-STATE.md Current State. Implement automated tier-3 batch runner that judges all scenarios on a schedule (weekly or per-release).

### P1 — No skill declares a testable phase-state machine

**Evidence:** Grep across all 62 `*/SKILL.md` files for phase declarations returned **zero matches**. Skills describe processes in prose ("Step 1: Reproduce", "Step 2: Root cause") but these are not machine-readable contracts. `create-skill/SKILL.md:86-109` defines frontmatter conventions (`inputs`, `outputs`, `chain`) but does NOT include `phases` or `execution_trace`.

**Impact:** There is no deterministic way to:
- Generate fixtures that trigger specific phases
- Validate that a skill run touched all expected phases
- Detect when a phase was silently skipped
- Measure per-phase coverage across the skill corpus

**Fix:** Add `phases` block to skill frontmatter or body convention. Example:

```yaml
phases:
  - id: P1-Init
    trigger: always
    reads: ["FRAMEWORK-STATE.md"]
    writes: [".svc/lane-tasks-<WI>.json"]
  - id: P2-Reproduce
    trigger: normal_mode
    reads: ["code", "tests"]
    writes: ["reproduction notes"]
  - id: P3-RootCause
    trigger: after P2
    reads: ["code", "logs", "spec"]
    writes: ["root cause 3-layer"]
```

### P1 — Tier-2 assertions check presence, not substance

**Evidence:** `test-framework/evals/tier-2/scenarios/diagnose-bug-typo.md:38-42`:
```
1. File exists
2. Identifies typo
3. Names file
4. Has root cause
5. Has pattern scan
```

Assertion 4 passes if the string "root cause" appears anywhere. Assertion 5 passes if "pattern" OR "grep" OR "search" appears. These are **keyword smoke tests**, not semantic validation. A brief that says "root cause: unknown" and "pattern: none found" passes all five assertions while being completely unactionable.

**Impact:** Tier-2 gives a false PASS signal. The tier-3 judge exists precisely because tier-2 is too weak, but tier-3 is too expensive to run per-scenario per-change.

**Fix:** Strengthen tier-2 assertions to require structured content (YAML frontmatter in briefs, mandatory section headers, non-empty required fields). Add a tier-2.5: fast mechanical validation of output structure before tier-3.

### P1 — No deterioration guard between skill iterations

**Evidence:** FRAMEWORK-STATE.md:66-71 documents the `diagnose-bug-typo` iteration history. v4 scored 10/9/9. v6 (after a template change) scored 6/8/9 — a regression. The framework detected this because a human was watching. There is no automated re-run of previously-passing scenarios after template changes.

**Impact:** Every skill edit is a potential regression across untested paths. The current process relies on human vigilance, which does not scale to 62 skills.

**Fix:** Before any SKILL.md edit, automatically re-run the full tier-2 scenario matrix for that skill. Block the edit if any scenario drops from PASS to FAIL. This is the "Phase 7: Deterioration guard" from the framework-evaluation-advisor model.

### P2 — Missing `framework-evaluation-advisor` skill

**Evidence:** No skill exists that automates the "run scenario → judge → identify gap → update template → re-run" loop. The tier-3 iteration that achieved 10/10/10 on `diagnose-bug-typo` required **8 manual prompt/template iterations** with human judgment at each step. This loop is:
- Repetitive (same pattern for every skill)
- Error-prone (v6 regression went unnoticed without human watch)
- Unscalable (62 skills × ~10 paths each = ~620 iterations)

**Impact:** Skill quality assurance is artisanal, not industrial. The framework cannot systematically improve its own skills without burning human attention on mechanical iteration.

**Fix:** Create `framework-evaluation-advisor` skill with 7-phase automation:
1. Parse SKILL.md → extract declared phases
2. Generate fixtures per phase
3. Run tier-2 phase-scenarios
4. Capture execution traces
5. Judge via tier-3 (completeness + actionability + consistency + **phase_coverage**)
6. Identify gaps and propose template fixes
7. Re-run full matrix to guard against deterioration

This skill is distinct from `evolve-framework` (finds gaps) and `test-framework` (runs tests). It is the **bridge**: it tells you WHICH tests to write and WHETHER your skill honors its contract.

---

### P2 — Judge variance requires multi-sample scoring, not single-run

**Evidence:** FRAMEWORK-STATE.md:74 footnote: "Consistency requires prior phase artifacts in judge prompt" — but does not mention that the **same brief scored 9/9/9 vs 10/10/10 on different runs**. This variance was observed during the `diagnose-bug-typo` tier-3 iteration (v8 vs v8-final).

**Impact:** Single-run tier-3 scores are noisy. A score of 7/8/9 could mean (a) the skill output is genuinely weak, or (b) the judge had a bad run. Framework decisions based on single samples are unreliable.

**Fix:** Tier-3 judge protocol should require 3 samples per dimension, taking the median. Report variance (`σ`) alongside score. Scores with σ > 1.5 require additional samples.

---

### P3 — Cross-model judge bias unmeasured

**Evidence:** All tier-3 judging so far uses Kimi judging Kimi outputs. There is no data on whether Claude judging Kimi outputs, or Kimi judging Claude outputs, produces systematically different scores. FRAMEWORK-STATE.md does not track judge-model / output-model pairs.

**Impact:** A skill that scores 10/10/10 under Kimi→Kimi judging might score 6/6/6 under Claude→Kimi. The framework has no way to detect this bias.

**Fix:** Run a calibration pass: judge the same 5 scenario outputs with 3 judge models (Kimi, Claude, Codex) and measure inter-rater reliability (Cohen's kappa). Add judge-model metadata to all tier-3 results.
