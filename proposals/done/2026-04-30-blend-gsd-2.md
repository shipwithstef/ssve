## Assessment A: Blend Opportunities

### 1. Artifact verification per unit type → `verify-promotion/SKILL.md` + `execute-changeset/SKILL.md`

**From:** `src/resources/extensions/gsd/auto-recovery.ts:verifyExpectedArtifact()` (gsd-2)
**Into:** `verify-promotion/SKILL.md` §Self-Verify + `execute-changeset/SKILL.md` §Close-out

**The problem in svc today:**
`verify-promotion` checks that files exist and tests pass, but it has no unit-type-aware verification. A milestone can pass verify-promotion with:
- A SUMMARY.md containing only `# BLOCKER` or `auto-mode recovery failed` (treated as complete because the file exists)
- Zero implemented ACs (all checked boxes are placeholder `[x]` inserted by the agent)
- No non-spec files changed (the milestone only touched `.gsd/` planning artifacts)
- Research phase skipped entirely (no RESEARCH.md) because the agent went straight to planning

This happened in WI-058 (GPS toggle) where the research phase was skipped, the plan had unchecked dependencies, and verify-promotion passed because the SUMMARY file existed and tests were green. The spec-code drift was caught 3 sessions later by `sync-spec-code`.

**How the source solves it:**
GSD-2's `verifyExpectedArtifact()` has bespoke logic per unit type:
- `research-milestone` / `research-slice`: verifies RESEARCH.md exists and contains findings, or accepts a PARALLEL-BLOCKER placeholder
- `plan-milestone`: parses roadmap and rejects zero-slice roadmaps
- `plan-slice`: requires task checkbox/heading patterns AND individual T{tid}-PLAN.md files for every task
- `execute-task`: uses DB status as primary; falls back to checked-checkbox in plan file
- `complete-slice`: checks UAT file + DB slice status
- `complete-milestone`: calls `hasImplementationArtifacts()` to reject milestones with only `.gsd/` files

Each check is mechanical — no LLM call. Failure writes a `# BLOCKER` markdown file and updates DB status, preventing false completion.

**What this changes in svc:**
- `verify-promotion/SKILL.md` gains a "Unit-type verification" subsection after the existing file-existence checks. For each unit type in the active WI, verify the corresponding canonical artifact has substance (not just existence):
  - DRAFT spec: contains ≥3 user stories with AC tables
  - UX-reviewed spec: contains screen flows with state coverage
  - DESIGNED spec: contains component specs with design token references
  - BASELINED spec: contains architecture decisions with trade-offs
  - EXECUTED changeset: contains non-spec file changes (git diff ≠ 0)
  - PROMOTED changeset: squash-merge clean, no unplanned files
- `execute-changeset/SKILL.md` gains a "Close-out verification" step before the AC/test mapping table. The agent must run the per-unit-type checks and report findings in the checkpoint.
- `land-changeset/SKILL.md` adds `hasImplementationArtifacts()` equivalent: if `git diff --stat` shows zero files outside `docs/specs/` and `.svc/`, flag as potential false completion.

**What NOT to take:**
- The SQLite DB dependency — GSD-2 uses `gsd.db` for state. svc uses file-based state. The verification logic should read files, not query a DB.
- The `native-git-bridge.ts` wrappers — svc already has git CLI patterns. Use existing `scripts/worktree.sh` and `git diff` calls.

**Why this matters:**
False promotion is the most expensive defect class in the pipeline. A falsely promoted changeset costs ~10× more to fix (new WI, new worktree, re-contextualization) than catching it at verify-promotion. WI-058 cost 3 sessions to recover. The `sync-spec-code` skill exists precisely because this happens — but it's reactive. Unit-type verification makes it preventive.

### 2. Auto-advance state machine → `route-workflow/SKILL.md`

**From:** `src/resources/extensions/gsd/auto-direct-dispatch.ts` + `dispatch-guard.ts` + `session-lock.ts` (gsd-2)
**Into:** `route-workflow/SKILL.md` §Autorun + framework lane execution discipline

**The problem in svc today:**
svc's autorun (`route-workflow` with autorun flag) advances one skill at a time, then stops. Between skills, the user must type `/next` or the session must be resumed. This creates three failure modes:
1. **Overnight loss:** A builder starts `write-spec` at 6pm, it completes at 6:30pm. The builder is away. The session compacts overnight. Next morning, the builder must re-read the spec, remember where they were, and manually invoke `design-ux`.
2. **Context loss at skill boundaries:** Each skill invocation starts fresh. The design-ux skill re-reads the spec from disk, but subtle intent ("I meant THIS not THAT") from the write-spec session is lost.
3. **Gate fatigue:** G1-G7 gates require explicit human approval. For experienced builders on familiar stacks, the gate becomes friction, not quality. The builder skips the gate via `--yolo`, losing the review value.

**How the source solves it:**
GSD-2's auto mode is a state machine that reads `.gsd/STATE.md`, determines the next unit, creates a fresh agent session, pre-inlines focused context, and lets the LLM execute. When finished, it reads disk state again and dispatches the next unit. Key mechanisms:
- `dispatch-guard.ts`: prevents out-of-order dispatch, respects `depends` declarations, deadlock avoidance
- `session-lock.ts`: `proper-lockfile` OS-level exclusive lock with PID metadata, stale lock cleanup, `onCompromised` recovery with 30-min grace period
- `crash-recovery.ts`: reads lock file on startup, detects interrupted sessions, emits synthetic `unit-end` events, provides recovery guidance
- `auto-supervisor.ts`: signal handlers, working-tree activity detection

**What this changes in svc:**
- `route-workflow/SKILL.md` autorun mode gains a "Level B — continuous advance" tier:
  - After a skill completes, `route-workflow` checks if the next skill's preconditions are met (file exists, gate passed, no blockers)
  - If met AND the builder has `auto_advance: true` in builder profile → auto-invoke next skill without human prompt
  - If not met OR `auto_advance: false` → stop with clear "Next: invoke `/design-ux`" message
- Session lock: `.svc/auto.lock` JSON file with PID, start time, active WI/skill. Prevents concurrent autorun from different hosts.
- Crash recovery: on session start, check `.svc/auto.lock`. If stale (dead PID or >30 min), emit recovery guidance. If active, warn and exit.
- Gate bypass policy: gates G1-G4 can be auto-passed for builders with `gate_trust_level: experienced` AND the skill's self-verify passes. G5-G7 always require human approval (execution quality, merge, verification).

**What NOT to take:**
- The full Pi SDK dependency — GSD-2 is a CLI tool with a runtime. svc is a methodology/framework. Auto-advance should be implemented as `route-workflow` logic, not a separate process.
- The `.gsd/STATE.md` format — svc already has `.svc/lane-tasks.json` and `docs/specs/project-state.md`. Use existing state files.

**Why this matters:**
Per FRAMEWORK-STATE.md Known Gaps: "Auto-advance state machine — MEDIUM — Level A is explicit across all skills; Level B branching/auto-eval still session-bound and host-dependent." This is a documented gap. GSD-2 proves the pattern works at scale (v2.78.1, production use). The hybrid opportunity: svc's 7 gates provide BETTER safety than GSD-2's unit-type verification alone. Combining auto-advance with svc's gate taxonomy means continuous execution with quality enforcement.

### 3. Memory extraction from transcripts → `manage-learnings/SKILL.md`

**From:** `src/resources/extensions/gsd/memory-ingest.ts` + `memory-extractor.ts` (gsd-2)
**Into:** `manage-learnings/SKILL.md` §Ingest + new `extract-learning` sub-skill

**The problem in svc today:**
`manage-learnings/SKILL.md` requires the user to explicitly say "what did we learn" or "add this learning." Three failure modes:
1. **Post-session amnesia:** After a 2-hour execute-changeset session, the builder remembers the big decisions but forgets the micro-insights ("oh, that package version doesn't work with Node 22").
2. **No cross-session surfacing:** A learning about Base44 RLS quirks written in session A is not surfaced when `design-tech` runs in session B, unless the builder manually searches.
3. **No behavioral validation:** Learnings are claims without evidence. "Always use X" might have been true in one context but not generalizable.

**How the source solves it:**
GSD-2's memory system has four entry points (note/file/url/artifact) and automatic transcript extraction:
- `ingestNote/ingestFile/ingestUrl/ingestArtifact`: persist source row to `memory_sources` table
- `extractMemoriesFromUnit()`: fire-and-forget background LLM call (Haiku, max 2048 tokens, temperature 0) that reads session JSONL, extracts assistant entries, and produces structured memories with categories (architecture, convention, gotcha, preference, environment, pattern) and actions (CREATE, UPDATE, REINFORCE, SUPERSEDE, LINK)
- Secret redaction: 10 regex patterns run before LLM ingestion
- Rate limiting: mutex + 30-second minimum interval
- Skip conditions: activity files < 1KB, already-processed units

**What this changes in svc:**
- `manage-learnings/SKILL.md` gains an "Auto-extract from session" section:
  - After any skill completes, `route-workflow` checks if the session produced a `.svc/session-*.jsonl` file
  - If yes AND `auto_extract_learnings: true` in builder profile → spawn background extraction
  - Extraction prompt: same categories as GSD-2 (architecture, convention, gotcha, preference, environment, pattern) but with svc-specific link relations (`related_to`, `depends_on`, `contradicts`, `elaborates`, `supersedes`)
- Secret redaction: add the 10 regex patterns to `hooks/svc-bash-guard.js` or a new `hooks/svc-secret-redaction.js` (runs on session JSONL before any external processing)
- Cross-session surfacing: `recall-stack-knowledge` (proposed in WI-SPINE-001) queries `docs/learnings/` by topic before loading a skill. Auto-extracted memories are deposited there.
- Behavioral validation: each extracted memory gets a confidence score (0.6–0.95). Memories with confidence < 0.8 require human confirmation before being added to the searchable corpus.

**What NOT to take:**
- The SQLite storage — svc uses markdown files. Store extracted memories as dated markdown files in `docs/learnings/auto-extracted/YYYY-MM-DD-<skill>-<WI>.md`.
- The `buildMemoryLLMCall()` dependency on Pi SDK — use the host's native LLM call (Claude/Kimi/Codex) with the same prompt.

**Why this matters:**
This directly addresses FRAMEWORK-STATE.md's knowledge gap: "Across ALL lanes, the framework rediscovers the same facts every session because knowledge isn't retrieved predictively." Auto-extraction makes every session deposit structured knowledge. The hybrid opportunity: svc's layered knowledge system (INDEX → CAPABILITIES → details) means extracted memories can be promoted to permanent knowledge layers when validated, creating compounding expertise.

### 4. Compaction snapshot → `references/context-budget.md`

**From:** `src/resources/extensions/gsd/compaction-snapshot.ts` (gsd-2)
**Into:** `references/context-budget.md` §Compaction protocol + `hooks/svc-pre-compact.mjs`

**The problem in svc today:**
When Kimi/Claude/Codex compacts context, all un-summarized state is lost. The builder returns to a compacted session and must reconstruct:
- What unit was active?
- What decisions were made in the last 10 turns?
- What was the last tool result?

This causes repetition, redundant tool calls, and token waste. AP-1 (orchestrator reads summaries not code) assumes summaries exist — but compaction doesn't always produce useful summaries.

**How the source solves it:**
GSD-2's `buildSnapshot()` produces a ≤2KB markdown digest before compaction:
1. Active context (current unit ID, phase, blockers)
2. Top 12 memories by rank
3. Recent `gsd_exec` runs (failures highlighted)

The snapshot is written to `.gsd/last-snapshot.md` and re-read after compaction.

**What this changes in svc:**
- `references/context-budget.md` gains a "Pre-compaction snapshot" protocol:
  - Before compaction triggers, the host hook (`hooks/svc-pre-compact.mjs`) writes `.svc/last-snapshot.md`
  - Content tiers: (1) active WI + skill + task ID, (2) last 3 decisions from `.svc/pipeline-decisions.jsonl`, (3) last tool result summary, (4) any open blockers
  - Max 2048 bytes — fits in even the tightest context windows
  - After compaction, the host reads `.svc/last-snapshot.md` and injects it as the first context message
- The snapshot format is machine-readable (YAML frontmatter + markdown body) so skills can parse it programmatically.

**What NOT to take:**
- The memory ranking algorithm — GSD-2 uses `getActiveMemoriesRanked(12)` which we haven't read. svc's version can use recency + manual priority flags.

**Why this matters:**
Context compaction is the #1 cause of session drift in long-running WIs. A 2KB snapshot costs ~500 tokens to inject but saves thousands of tokens in repeated re-discovery. The hybrid opportunity: svc's `.svc/pipeline-decisions.jsonl` is already a structured decision log. The snapshot simply extracts the last N entries — no new storage needed.

### 5. Tool-call loop guard → `hooks/svc-loop-guard.js`

**From:** `src/resources/extensions/gsd/bootstrap/tool-call-loop-guard.ts` (gsd-2)
**Into:** `hooks/svc-loop-guard.js` + `references/anti-patterns.md` AP-26

**The problem in svc today:**
Stuck loops are the #2 token waste after compaction. Common patterns:
- `read_file` on the same path 12× in a row (agent forgot it already read it)
- `grep` for the same pattern 8× (agent didn't check results)
- `bash ls` in the same directory 5× (agent is stalling)

The existing `hooks/svc-loop-guard.js` detects generic loops but doesn't have signature-based detection.

**How the source solves it:**
GSD-2's loop guard uses SHA-256 signature hashing:
- Each tool call is hashed (tool name + args normalized)
- Signatures are stored in a ring buffer
- If the same signature appears N times within M turns, the loop is detected
- Escalation: notify user, suggest `undo`, or auto-abort

**What this changes in svc:**
- `hooks/svc-loop-guard.js` gains signature-based detection:
  - Hash: `SHA256(toolName + canonicalArgs)` where canonicalArgs sorts keys and normalizes paths
  - Trigger: same signature ≥3 times within 10 turns
  - Action: block the tool call, inject a reminder message ("You've already run this tool 3 times. Results: <last result>. Consider: <suggestion>"), and log to `.svc/pipeline-decisions.jsonl`
- `references/anti-patterns.md` adds AP-26: "Tool-call stuttering — repeated identical tool calls without new information"

**What NOT to take:**
- The exact hash algorithm — SHA-256 is fine but simpler hashes work for short signatures. Keep it lightweight.

**Why this matters:**
Each stuck loop costs $0.50–$2.00 in tokens. A 12-turn `read_file` loop on a 500-line file at $3/Mtok is ~$1.50. With 50+ skills and hundreds of sessions, this adds up. The guard pays for itself in one prevented loop.

## Assessment B: External Addon Viability

**Runtime addon?** NO
**License:** MIT (compatible)
**Install:** N/A

**Why not addon-viable:**
GSD-2 is a standalone CLI application (`gsd-pi`), not a library or framework. It does not expose a programmatic API — all interaction is via shell commands, exit codes, and JSON/JSONL output. While svc skills can shell out to `gsd headless`, this would create a dependency on a Node.js CLI tool that manages its own worktrees, sessions, and state. svc already has its own worktree model (`scripts/worktree.sh`), session model (`.svc/lane-tasks.json`), and state model (`docs/specs/project-state.md`). Running GSD-2 inside svc would create two competing state machines.

**What svc should NOT rebuild:**
- The Pi SDK (pi-ai, pi-coding-agent, pi-tui) — svc is framework-agnostic and works across all LLM hosts (Claude, Kimi, Codex, Gemini, OpenCode). Rebuilding the Pi SDK would duplicate host-specific integration work.
- The native Rust engine — svc is a documentation/script framework. Native modules are out of scope.
- The Electron studio / VS Code extension — svc has no IDE integration today. These are product features, not framework features.

**What svc should still own:**
- Pipeline orchestration (7 lanes, 7 gates) — svc's progressive narrowing is more granular than GSD-2's milestone→slice→task hierarchy
- Knowledge system (3-layer persistent expertise) — svc's library vs project separation is more disciplined than GSD-2's memory table
- Builder profiling — unique to svc
- Review gate taxonomy (G1-G7) — more comprehensive than GSD-2's verification
