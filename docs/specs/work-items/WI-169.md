## Problem

The capability matrix produced by `catalog-domain-capabilities` knows that a project has table-stakes capabilities like multi-language, theme-switching, auth-state. But that knowledge sits as documentation. It does NOT trigger journey generation for the user-facing flows of those capabilities.

Example Marketplace example: capability matrix already lists "multi-language (FR/BG/EN)". Stack already wires `i18n` (`getNavTranslations`, `dispatchEvent('languageChange')`). Yet zero journeys cover language switching. Result: WI-196.

## Proposal

When `catalog-domain-capabilities` populates the matrix and finds a row matching a recognized table-stakes capability AND the project's tech-stack matches the canonical implementation pattern:

1. Auto-invoke `write-journeys --capability=<name>` to produce journey skeletons for that capability.
2. Output: `docs/specs/journeys/J-CAP-<capability-slug>.feature.md` with all standard role × surface combinations covered.

**Recognized capabilities (initial set):**

- `multi-language` (i18n) — produces journey covering language switch on every authenticated chrome surface
- `theme-switching` (dark/light) — produces journey covering theme toggle on every authenticated chrome surface
- `auth-state-recovery` — produces journey covering OAuth resume / token refresh / sign-out on every entry point
- `multi-locale-payments` — produces journey covering currency / locale switch in checkout
- `accessibility` — produces journey covering keyboard nav, screen-reader, focus management

**Stack matchers (so WI-169 doesn't false-fire on greenfield without the impl):**

- multi-language: presence of `i18n.js`, `react-i18next`, `vue-i18n`, OR a `getTranslations`-style function in Layout
- theme-switching: presence of a `ThemeProvider` / `useTheme` / `<ThemeToggle>` component
- auth-state-recovery: presence of `AuthContext` / `useAuth` / OAuth callback handler

## Acceptance criteria

- AC1: In Example Marketplace, running `catalog-domain-capabilities` after WI-169 ships produces `J-CAP-multi-language.feature.md` automatically.
- AC2: The journey covers customer × mobile, customer × desktop, owner × mobile, owner × desktop combinations.
- AC3: Idempotent — re-running doesn't duplicate.
- AC4: Stack matchers correctly skip capabilities not implemented in the project (no false fires).

## Cost estimate

2-3 hours framework work after WI-168 lands.

## Dependencies

Builds on WI-168's chrome-discovery primitive.

## Counterfactual

When you add Spanish translation to Example Marketplace: capability matrix already says "multi-language" is in scope. WI-169 auto-files a "verify Spanish lang switch on mobile + desktop × customer + owner" journey. Without it: you'd add Spanish, ship it, hit the same body-pointer-events bug class for Spanish specifically — three more iterations like WI-184 → 195 → 196.
