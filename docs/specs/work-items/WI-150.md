# WI-150: Add review-plan and review-security to corePackForRouting in skills-manifest.json

**Type:** framework
**Status:** VERIFIED
**Severity:** HIGH
**Filed:** 2026-05-08
**Source:** route-workflow framework audit

## Audit Verdict — RESCOPE (do not blind-add)

**Bundle with WI-159** — same underlying design question.

The exclusion is **likely intentional**: `review-plan` and `review-security` are auto-invoked **gates** that fire between other skills (e.g., review-plan runs after plan-changeset, before execute-changeset). They are not user-routable entry points. The `corePackForRouting` docstring says "routing-safe baseline used by route-workflow" — gates don't belong there because route-workflow doesn't suggest them; the upstream skill invokes them.

**Ship plan (rescoped):**
1. Convert this WI from "add to corePackForRouting" → "**document why review-plan/review-security are excluded**".
2. Run `discuss-phase` together with WI-159 to settle the design call:
   - Option A: gates stay excluded; add a `## Why these are excluded` block to `corePackForRouting` schema docstring.
   - Option B: gates become first-class; add to both `corePackForRouting` and `pipeline` array, update route-workflow's intent table to allow direct invocation.
3. Whichever option wins, add a tier-1 validator that the chosen invariant holds (either "gates absent from corePackForRouting" or "gates present").

**Do not ship as filed** — would conflate gate skills with routable entry points.

## Problem
`review-plan` and `review-security` are in `includedSkills` but excluded from `corePackForRouting`. The routing-rules.md Core Pack is documented as the "routing-safe baseline," yet two mandatory gates are missing.

## Impact
Automated routers and linters trusting `corePackForRouting` cannot find these skills. review-plan is the gate between plan-changeset and execute-changeset; review-security is mandatory for auth-sensitive changes.
