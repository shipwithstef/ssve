# WI-354: Active user intent isolation and stale completion guard suppression

## Problem

A Stop-hook completion guard for a stale Example Marketplace `WI-335` task graph overrode
the newest user intent. The user was discussing accounting and launch-vehicle
decisions, but the guard injected pending `WI-335` deployment tasks and told the
assistant to execute them. The assistant followed the guard, deployed and
verified `WI-335`, and the user had to correct the session with "what are you
doing this was a talk about totally unrelated thing?" A second `WI-335`
completion guard appeared after that correction.

WI-352 fixed WI-scoped isolation for parallel hooks and worktrees, but this is
a different axis: a correctly resolved active WI can still be stale relative to
the latest user prompt.

## Proposed Fix

Add a small active-intent guard that bridges UserPromptSubmit and Stop hooks:

1. Prompt-time writer:
   - Use `hooks/svc-prompt-stale-state.mjs` or a new helper such as
     `hooks/lib/active-intent.mjs`.
   - Parse the latest user prompt for explicit correction, unrelatedness, stop,
     ignore, and `continue WI-XXX` signals.
   - Persist a session/cwd scoped state file under `.svc/` with latest prompt
     hash, classification, suppressed WI list, and optional resumed WI.

2. Stop-hook reader:
   - Read the active-intent state before `svc-task-completion-guard.sh` emits a
     hard block.
   - If the resolved WI is suppressed for the current cwd/session, downgrade to
     advisory or allow stop.
   - If the latest prompt explicitly resumes that WI, clear suppression and use
     normal completion-guard behavior.

3. Route-workflow protocol:
   - Make active user intent isolation a mandatory guard reconciliation rule.
   - Keep human-invoked route-workflow in prompt-composer mode for this replay
     and route to `improve-framework`.
