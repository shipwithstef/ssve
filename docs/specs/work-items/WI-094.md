## Goal
A persistent meta-orchestrator that tracks every AI/dev resource the builder owns (capabilities, quotas, reset windows, side-tools), holds shared state across all projects + the framework itself, and actively recommends moves that (a) ship existing projects to revenue and (b) spot side-earning opportunities the builder would otherwise miss — so the framework can self-fund and self-improve.

## Context
The builder owns a stack of paid + free AI/dev resources but currently uses each in isolation, only when they happen to remember it exists, and only inside one project at a time. Concrete inventory at filing time (illustrative — actual values must be queried/maintained dynamically):

| Resource | Notable separate capabilities |
|---|---|
| GPT Business | Codex CLI; Deep Research is **separately metered**, not consumed by Codex usage |
| Claude Max ×5 (5-person plan) | Claude Code CLI; Claude design tool / timer in beta is a **separate** budget |
| Kimi $39 | Kimi CLI; possibly separate quotas |
| Gemini Pro | gemini-cli; Gemini app features (Deep Research, etc.) outside CLI |
| MiMo (Xiaomi standard) | mimo CLI; Hermes agent / clawing capabilities exist outside the default invocation path |
| Base44 $50 + free credits | hosted backend / app builder |
| Namecheap | 1-month marketing trial — currently sitting unused |

The unmet need is not "another skill that audits my budget once." It is a **standing concierge** that:

1. Holds a live inventory of resources, quotas, reset windows, separate-budget capabilities, and which CLI/host each resource maps into.
2. Has cross-project + framework-wide visibility (read-only) — knows what's in flight, what's blocked, what's idle.
3. Surfaces moves the builder would not have thought of: "you have a Namecheap marketing trial sitting unused — Example Marketplace is the right project to point it at this week"; "MiMo's Hermes agent could do this scrape that Claude is about to burn $X on"; "Deep Research on GPT Business is unused this cycle and could close this open question for free."
4. Reasons about cash flow honestly: small bets that fund bigger bets — "$3 spend here may yield $100, route it." Output reinvests into more agents / horsepower for framework self-improvement.
5. Diagnoses the actual bottleneck behind "great framework, no shipped revenue product" and proposes the smallest sequence of moves to fix it.

The builder explicitly named the bottleneck this WI must solve: Example Marketplace is unfinished → no revenue → can't afford Claude Max → wants to leave Base44 but can't yet → can't even start a React Native port → unused marketing trial expiring → framework keeps improving but doesn't earn. Without an orchestrator that holds all of that simultaneously, the builder cannot break the loop alone.

## Hypothesized Value
The framework starts paying for itself. Builder ships Example Marketplace because the orchestrator routes resources to that goal instead of leaving them latent. Side-earning skills get spawned when the orchestrator notices an opportunity that doesn't compete with the main goal. Reset-window awareness stops wasted spend (e.g. paid-tier work happening when a free-tier window is open).

## Broad Scope
- **Persistent capability registry** (per-builder, cross-project): JSON in `~/.svc/capabilities/` listing each resource, separate sub-budgets, quota, reset cadence, current consumption estimate, last verified date, and the host(s) it maps into.
- **Shared state across projects + framework**: read-only access to every project's `docs/specs/project-state.md`, work-item INDEX, and learnings; framework's `FRAMEWORK-STATE.md`. The orchestrator never mutates project state; it advises.
- **Recommendation engine** with three lenses, all running on every invocation:
  1. **Ship-the-current-project lens**: what's the smallest move that gets the highest-priority unfinished product (currently Example Marketplace) closer to first revenue?
  2. **Idle-resource lens**: which paid/trial resources are under-used this reset window? Where can they be applied right now (this project, another project, framework, or a side-earning bet)?
  3. **Side-earning lens**: spot small-bet opportunities — domains, scripts, micro-tools, content surfaces — that could earn while the main project ships. Output a tiny WI in the relevant repo if the builder accepts.
- **Cash-reinvestment doctrine**: any earned revenue is presumptively re-invested in agents/horsepower for framework self-improvement until a configurable runway threshold is met. Make this explicit in the recommendation output.
- **Capability re-discovery**: periodically re-check vendor pages / changelogs for new separate-budget capabilities (e.g. "Claude design tool moved out of beta", "Gemini Pro added Deep Research minutes"). Flag and update the registry.
- **Honest diagnosis output**: on demand, the orchestrator must answer "why have I not shipped a revenue product despite owning this framework?" with a specific, evidence-graded answer pointing at concrete blockers across resources, projects, and behaviors — not platitudes.

## Persona Fit
Solo builder / framework operator with multi-vendor stack. The only persona that benefits from this exists explicitly because the framework + the builder's tool sprawl outpace what one human can hold in working memory.
