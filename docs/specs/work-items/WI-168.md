# WI-168: write-journeys --auto-discover-chrome

## Problem

`write-journeys` reads feature specs forward and never reads rendered chrome (`Layout.jsx`, `MobileHeader.jsx`, `Sidebar.jsx`) backward. Every interactive control rooted in chrome (not a feature spec) is invisible to journey generation. Example Marketplace recurrence: language switcher had ZERO journey coverage despite 50+ shipped i18n PRs.

## Proposal

Add `--auto-discover-chrome` mode to `write-journeys`:

1. Parse Layout/MobileHeader/Sidebar files for interactive control roots (`<button`, `<Select`, `<Sheet`, `<DropdownMenu`, `<Drawer`, `<a href`, `<Link`, `<NavLink`).
2. Extract visible label + role + container.
3. Cross-reference against existing journeys.
4. For each uncovered control, emit a skeleton scenario in `docs/specs/journeys/Chrome-<role>-<surface>.feature.md`.

**Heuristics for emitted journeys:**
- Sheet/Drawer/Dialog: "open → close → app remains interactive" (the WI-195/196 class)
- Select/DropdownMenu: "open → pick option → can still interact"
- Locale-aware controls (i18n, theme toggle): "switch → all text updates → can still interact"

## Acceptance criteria

- AC1: Running `write-journeys --auto-discover-chrome` in Example Marketplace produces ≥1 new chrome journey covering the language switcher.
- AC2: Idempotent — doesn't duplicate existing journeys.
- AC3: SUMMARY.md cites file:line for each chrome control found.
- AC4: Tier-1 validator pins behavior on a fixture project.

## Closeout

Closed 2026-05-10. `write-journeys` now documents Mode 8: Chrome Auto-Discovery and ships a deterministic helper at `write-journeys/scripts/auto-discover-chrome.mjs`. The helper scans chrome-surface files (`Layout`, `Header`, `Sidebar`, `Nav`, `Chrome`, `Shell`, `Menu`) for interactive roots, emits idempotent `docs/specs/journeys/Chrome-*.feature.md` skeletons with stable `@chrome-control:<id>` traces, and writes `docs/specs/journeys/SUMMARY.md` with file:line evidence for every found control.
