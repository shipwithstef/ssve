# WI-386: Conditional plan blueprints (kill the Opus-priced double-spend on the inline path)

**Status:** in_progress
**Lane:** framework
**Size:** M
**Stage:** S4
**Source:** flow-architecture audit (wf_e0063433), 2026-06-08

## Problem
`plan-changeset` mandates full file contents for every CREATE; `execute-changeset` says "Write once… No double-spend" — code is authored at PLAN prices then re-applied at EXEC. WI-357 swapped EXEC to Sonnet (doesn't need code dictation) but left the blueprint architecture intact. Empirically `.svc/dispatch-log.jsonl` has 5 lifetime entries, ALL opus-override inline — the zero-context executor path has never actually run.

## Mechanism
Keep full blueprints as the executor contract, but make them CONDITIONAL on actual zero-context dispatch (`DISPATCH=mimo-pro|sonnet`). When the orchestrator executes INLINE with full context already loaded (the only mode used in practice), skip blueprint authoring entirely.

- [x] Negative fixture: a dispatch-mode manifest WITHOUT blueprints is rejected. — `test-framework/evals/tier-1/validate-conditional-plan-blueprints.sh` builds absent-mode + explicit-`dispatch` fixtures and asserts BOTH the schema engine and the real `emit-receipt.mjs` reject them (12/12 pass); the absent-mode case is the load-bearing fail-closed assertion.

## Value-preservation
Value-neutral, increases efficiency: preserves WI-347's zero-context isolation guarantee for the dispatch path; only the redundant transcription on the inline path is removed. LOW risk.

## Vision fit (whole-company / versatile PM)
Stops paying the architect to redraw blueprints the builder will never read — eliminates double-work between the planning and building roles so the company's labor isn't billed twice.

## Relationships
Amends WI-347 (declare it the superseded contract; still `status:open` in INDEX despite shipped code). Composes with WI-380 (agents write code once from the contract).

**WI-347 supersession:** WI-347's AC "Require `changeset_blueprints`... arrays" (unconditional) is hereby narrowed to "require `changeset_blueprints` UNLESS the receipt self-declares `mode: inline`." The zero-context isolation guarantee WI-347 protects is preserved verbatim for the dispatch path — only the inline path (full-context orchestrator, the only mode `.svc/dispatch-log.jsonl` has ever recorded) is exempted from the redundant transcription. Fail-closed: absent/unmarked `mode` keeps WI-347's hard requirement.

## Tier-1 promotion note
(required by `rules/tier-1-promotion.md`)

- **validator_path:** `test-framework/evals/tier-1/validate-conditional-plan-blueprints.sh`
- **failure_class:** Conditional-requirement fail-OPEN regression. WI-386 relaxes a previously-unconditional schema requirement (`changeset_blueprints`) behind a `mode` gate. If the conditional is mis-encoded — the vacuous-`properties` draft-07 trap, a cwd-relative schema load that returns null (the live WI-396 regression on `emit-receipt.mjs`), or the chain engine and the declarative schema drifting apart — the gate silently accepts blueprint-less DISPATCH-mode plan-manifests, destroying WI-347's zero-context executor guarantee. The validator asserts BOTH enforcement layers fail-closed against the absent-mode fixture.
- **promotion_signal:** Signal 3 (protects a framework hot path in `rules/plan-changeset-trigger.md`: `schemas/receipts/*`, `scripts/check-chain-receipts.mjs`, and `scripts/emit-receipt.mjs` all run on every commit/push via the pre-push receipt gate — a regression blocks promotion verification or, worse, fails open and lets unverifiable plans land). Also Signal 2-adjacent: the cwd-skip fail-open class is documented in `check-chain-receipts.mjs` (WI-396) and `references/anti-patterns.md`.
- **expected_runtime_budget:** < 5s (measured 0.53s: python `jsonschema` over 4 in-memory receipts + 3 `emit-receipt.mjs` runs in a throwaway empty git repo; no network, no LLM, no real receipts/notes).
- **why_tier_2_or_targeted_is_insufficient:** The schema + the two custom validators are read on EVERY commit and push, not on a feature surface a tier-2 scenario would exercise. A fail-OPEN here is invisible to product-level QA (the receipt still "validates") and only surfaces as a missing-blueprint executor failure deep in a later dispatch — too late, and off the path tier-2 covers. The check must run on the hot path's own lint so a schema/engine edit that re-opens the gate is caught before merge. It is hermetic and sub-second, so it earns the always-on slot without budget cost.
