# WI-304: route-workflow closeout can leave main ahead of origin

## Problem

After closing WI-179/WI-180/WI-185, `main` was clean but `git status --short --branch`
reported `main...origin/main [ahead 99]`. The work was locally committed and
validated, but not published to `origin/main`.

## Impact

Framework work can appear complete in local closeout while the shared remote
state is stale. That leaves the next host/session/user looking at old framework
behavior and makes post-merge validation claims misleading.

## Fix

`route-workflow/SKILL.md` now has a `## Publication-State Closeout` section.
For mutating framework work on `main`, closeout must:

- run `git status --short --branch`
- run `git fetch --prune origin`
- compare `origin/main...HEAD`
- push `main` when local commits are intended to be published and remote can
  fast-forward
- report the push result or exact blocker
- state whether local `HEAD` and `origin/main` match

## Acceptance Criteria

- AC1: `route-workflow` requires a publication-state closeout for mutating
  framework work.
- AC2: The closeout names clean/dirty state, remote divergence, push result or
  blocker, and HEAD/origin parity.
- AC3: A tier-1 validator fails if the route-workflow publication-state section
  or self-verify row is removed.
- AC4: The original local-ahead state is resolved by pushing `main`.

## Verification

- `git push origin main` published `f0ad38b..3304135`.
- `git status --short --branch` reported `## main...origin/main` after push.
- `bash test-framework/evals/tier-1/validate-route-workflow-publication-state.sh` - PASS.
