# WI-353: Solution confidence protocol defaults to automatic design-to-implementation flow

## Problem

The user asked for two separate changes:

1. A framework capability change: when a user asks to be confident the design is
   right, the framework must automatically build the current picture, evaluate
   suggestions, compare options, account for cost/cache/user impact, and only
   then decide the solution.
2. A product/application change: Example Marketplace discovery performance and location
   loading need a separate decision/design/implementation path.

The framework change was implemented as a proposal and state update, but it was
not visible as its own work item. That made it look like only the Example Marketplace item
existed.

## Required Behavior

- Default mode is `design_auto`.
- Human gates are not default.
- `post_design_human_gate` is used only when the user explicitly asks to review
  or approve after design.
- `intake_only` is used only when the user explicitly asks for no design,
  no decision, no plan, or only a parked WI.
- External suggestions from Base44 or other assistants are triaged as evidence:
  `adopt`, `modify`, `defer`, `reject`, or `unrelated`.
- The confidence artifact must cover current implementation, why the current
  shape may exist, web/mobile/native surfaces, cost/cache/freshness, at least
  five real-world examples, alternatives, tradeoffs, and final direction.
- The delivery graph compiler and validator must carry this as core state, not
  only prose in skill instructions.
