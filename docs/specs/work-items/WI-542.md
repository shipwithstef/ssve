## Problem

Every Grok session paints **SessionStart 1** red. The hook is
`svc-session-start-healthcheck.mjs` loaded from `~/.claude/settings.json`
via Grok Claude-compat (`global/settings:session_start[1]`). It is killed
at Grok's default **5s** observe-hook timeout while it re-runs
`./setup --host grok` against 11 "missing" hook scripts that are not
missing.

## Evidence

Recorded on three consecutive Grok sessions on 2026-08-17:

| Session | Result |
|---|---|
| `01a00df9` (this report) | `timed out after 5000ms` (5019ms) |
| `01a00df0` | `timed out after 5000ms` (5022ms) |
| `01a00de5` | `timed out after 5000ms` (5018ms) |

Replay of the hook (canonical script under `~/.grok/skills/hooks/`):

```
[svc-session-start:grok] self-heal: detected 11 issue(s) (0 dangling, 11 missing hook script(s)), re-running setup
[svc-session-start:grok] self-heal: 11 issue(s) still present after setup (exit=0).
elapsed=14.41s first run, 7.43s / 5.74s after
```

The 11 "missing" paths are the TOML regex slicing `~/.grok/skills/hooks/foo.mjs`
into `/.grok/skills/hooks/foo.mjs`. The real files exist. Setup cannot
repair a parser lie, so every session pays a 6–14s self-heal and Grok
kills it at 5s.

Sibling: `~/.kimi/config.toml` uses the same `~/.kimi/skills/hooks/*.mjs`
portable commands. The same parser will false-positive Kimi whenever
that host's healthcheck runs.

## Root cause (one line)

`findMissingHookScripts()` treats the `/` inside a portable `~/...mjs`
path as an absolute filesystem path, so a healthy Grok/Kimi install
looks broken and SessionStart self-heal overruns Grok's 5s default.
