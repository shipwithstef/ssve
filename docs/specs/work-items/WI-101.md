# WI-101: capture-idea self-exclusion missed post-merge proposal moves

**Type:** bugfix
**Status:** VERIFIED
**Closed:** 2026-04-24
**Merged PR:** #14
**Severity:** medium
**Filed:** 2026-04-24
**Source:** framework-session observation (A5 in evolve-framework tier-A queue; learning `capture-idea-self-exclusion-misses-post-merge-proposal-move` conf 8)
**Lane:** framework

## Goal

Prevent `capture-idea --from-proposal` from emitting a duplicate WI when a proposal has already been promoted and its file moved from `proposals/` to `proposals/done/` by a prior merge.

Observed failure: a parallel session re-captured `2026-04-24-framework-improvement-symlink-refresh-after-worktree.md` from `proposals/done/` and emitted WI-081 even though WI-079 already covered the same proposal.

## Root Cause

`findExistingWiByAnchor()` matched existing WIs only on the leaf anchor (`§ P<N>.<M>` for phased, `§ <basename>` for monolithic). For monolithic proposals, `renderWi` writes Source as a bare path (`proposals/foo.md`) without the `§` anchor, so `sourceLine.includes("§ foo")` never matches — the guard silently no-ops.

## Fix

`findExistingWiByAnchorOrBasename()`:
- Anchor match first (preserves phased-leaf precision).
- Falls back to proposal-basename match in the Source line. Basename check is applied **only for monolithic proposals**; for phased proposals all leaves share the same basename and a basename-only match would falsely skip every sibling.

## Acceptance Criteria

- **AC-01** Pre-existing WI whose Source references `proposals/foo.md` causes `capture-idea --from-proposal proposals/done/foo.md` to emit 0 new WIs for the monolithic case.
- **AC-02** Phased proposals retain per-leaf self-exclusion (sibling leaves of a re-captured proposal still emit independently).
- **AC-03** Existing regression `self-exclusion: P0.1 skipped, 2 new WIs emitted` continues to pass.
