# WI-520: Bare-basename citation resolution can bind the import-shape check to the wrong file

**Type:** framework defect
**Status:** identified
**Severity:** medium
**Filed:** 2026-08-04
**Source:** WI-512 global cross-batch review
**Lane:** framework

## Problem

`scripts/branch-index-freshness.mjs` `extractCitedFiles` resolves a citation token in tiers. The two-segment tier (`endsWith('/' + token)`) is sound. The final tier is a bare-basename `allFiles.find(...)` — **first match wins across the whole repo**.

A short-form citation like `index.ts:10` — precisely the form this file's own comments record as normal in real indexes — will bind to an arbitrary `index.ts`. The import-shape check then watches a file the index never cited, and fails to watch the one it did. Both directions are wrong: a false `import-shape` finding on an unrelated file, and silence on the real one.

This matters more than its severity suggests, because this resolution is the mechanism the claim *"closes the one measured false-GREEN hole"* rests on. WI-512 fixed the check so it can flip green→red; this is about it flipping on the right file.

## Fix direction

Refuse ambiguity rather than resolving it arbitrarily. When a bare basename matches two or more tracked files, report the token as unresolvable — naming the candidates — instead of silently picking one. An index that cites ambiguously should be told to disambiguate; that is a cheap authoring fix, and it is strictly better than a check that quietly watches the wrong file.

## Acceptance criteria

- [ ] **AC-1** A bare-basename token matching ≥2 tracked files is reported as ambiguous, with the candidate list, and is not resolved.
- [ ] **AC-2** Unambiguous bare basenames still resolve, and the two-segment and full-path tiers are unchanged.
- [ ] **AC-3** An ambiguous citation does not silently suppress the import-shape check for the file that *was* meant.
- [ ] **AC-4** Coverage for the ambiguous case, so the arbitrary-pick behavior cannot return.
