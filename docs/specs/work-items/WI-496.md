# WI-496: Codex bootstrap exit unusable in onboarded product repos — bind sanctioned script to the installed skills root

**Type:** bugfix
**Status:** identified
**Severity:** critical
**Filed:** 2026-07-18
**Source:** live Codex session in `~/app-workspaces/example-marketplace` — the WI-494 recovery command itself denied; owner directive: proper fix, lean chain
**Lane:** framework
**Related:** WI-494 (introduced the bootstrap exit; R2-F001 deferred the absolute-path binding this WI now applies), WI-487 (installed-enforcement pattern reused)

---

## Problem (root cause)

WI-494's zero-state bootstrap exit (`bootstrapShapeInner` in
`hooks/codex/svc-codex-skill-load-enforcer.mjs`) authorizes exactly one command:
`node scripts/svc-ensure-worktree.mjs ...` — and validates it by
`fs.realpathSync(path.resolve(ctx.repo_root, "scripts/svc-ensure-worktree.mjs"))`,
returning `false` when that throws, plus a `startsWith(repo_root)` fence that rejects
any resolution outside the governed repo (so a symlink cannot satisfy it either).

That assumption only holds in the **framework repo**, where the script is a real
tracked file. **Onboarded product repos do not vendor svc scripts** — `example-marketplace`
has `scripts/task-graph.mjs` but no `svc-ensure-worktree.mjs`; svc lives at the
installed skills root (`~/.codex/skills/scripts/`). Net effect: in every product repo
the guard denies all governed mutation AND its own printed recovery command, which is
the exact deadlock class WI-494 was shipped to eliminate. Reproduced live: the
deployed enforcer denies `node scripts/svc-ensure-worktree.mjs --wi WI-494 --branch
wi-494-social-favourites` from a clean zero-state `example-marketplace` (cwd == repo root,
argv-lex ok, laneGraphs == 0) solely because the script path cannot resolve.

WI-494's own reviewer proposed the fix ("bind to an absolute canonical script path")
as R2-F001; it was consciously deferred to keep the framework-repo relative spelling
natural. This WI applies it, host-aware.

## Fix

In `bootstrapShapeInner` (and the `deny()` recovery string):

- Compute TWO canonical script realpaths: **repo-local**
  (`repo_root/scripts/svc-ensure-worktree.mjs`, current behavior) and **installed**
  (`<enforcer's own install root>/scripts/svc-ensure-worktree.mjs`, derived from
  `import.meta.url` exactly like the WI-487 durable-source pre-check — trusted
  because it is the running enforcer's own tree; never from env or payload).
- Accept `argv[1]` when its realpath equals **either** canonical (repo-local keeps
  priority; the installed form is the product-repo path). The `startsWith(repo_root)`
  fence applies only to the repo-local arm; the installed arm must realpath-equal the
  enforcer's own sibling script — no third location can pass.
- All other WI-494 fences unchanged: cwd == repo_root, argv-lex strict flags,
  laneGraphs()==0 zero-state gate, marker ownership.
- `deny()` recovery prints the command that will actually work in the current repo:
  repo-local when it exists, else the installed absolute path.
