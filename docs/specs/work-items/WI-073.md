## Goal

Give `capture-idea` a `--from-proposal <path>` mode that converts a reviewed proposal file into one or more work items, validating the proposal → WI seam that currently requires manual copy.

## Context

The framework pipeline `evolve-framework → improve-framework → (proposal) → work-item → plan-changeset → …` has no owning skill for the proposal → work-item step. Today it is manual copy. `capture-idea` is already the WI-intake skill, so extending it with a proposal-aware mode is the lowest-surface fix (vs. adding a sibling skill). Closing this seam unblocks Phase 0.2 onward of the cohesion plan — every subsequent WI should flow through this mechanism instead of direct `write-spec`.

Direct consequences of the current state:
- Proposal Goals / ACs / File Impact blocks are re-typed into the WI template by hand, introducing drift.
- No deterministic "this proposal produced these WIs" audit trail.
- No enforced `proposals/done/` archival with a back-reference to the emitted WI(s).

## Goals

1. `capture-idea` accepts `--from-proposal <path>` alongside its existing intake modes.
2. When used, the skill parses the proposal's `## Goals`, `## Acceptance Criteria` (or equivalent per-phase AC blocks), and `## File Impact` (or `Scope boundary`) sections and emits one `docs/specs/work-items/WI-NNN.md` per promotable leaf item in the proposal, pre-filled with Subject, Type, Status (`DRAFT`), Severity, Source (the proposal filename), Lane (`framework` if the proposal lives under `proposals/`), and copied AC list.
3. The source proposal moves to `proposals/done/` with a trailer `**Promoted to:** <list of WI files>`.
4. A `taste` decision entry appended to `.svc/pipeline-decisions.jsonl` names the proposal path and the emitted WI IDs.
5. The mode is additive — existing `capture-idea` intake behavior is unchanged.

## Non-Goals

1. Promoting the WIs onward through plan-changeset/execute-changeset — that's downstream.
2. Triaging or ranking the emitted WIs — they inherit the proposal's ordering.
3. Cross-repo work-item creation (e.g., writing into a different project's `docs/specs/work-items/`) — out of scope; proposal and WI live in the same repo.
4. Validating the proposal content itself — `review-plan` already does that upstream.
5. A standalone CLI wrapper (`scripts/capture-idea-cli.mjs`) — unless determined necessary during plan-changeset. The mode should be reachable via the host's standard skill-loading path first.

## User Stories

### US-01 — As a framework maintainer, I want to promote a reviewed proposal into work items with one invocation

**Why:** eliminates manual copy between proposal blocks and WI templates; preserves the audit trail.

- **AC-01.1** Invoking `capture-idea` with `--from-proposal proposals/<date>-<name>.md` on a proposal that has an explicit phased plan with leaf items (e.g., P0.1, P0.2, …) produces one WI file per leaf, named `docs/specs/work-items/WI-NNN.md` where NNN is the next integer after the highest existing WI. **Self-exclusion rule:** any leaf whose `Source` anchor matches the `Source` field of an already-existing WI file is skipped (per Codex v1 review #5). This prevents WI-073 from being duplicated when the mechanism is run against its own source proposal.
- **AC-01.2** Each emitted WI contains, at minimum: Type, Status (`DRAFT`), Severity, Filed date (today), Source (proposal path + leaf anchor like `§ P0.2`), Lane, Goal, Goals list, Non-Goals list (copied verbatim if present), the proposal's AC block for that leaf, and File Impact scope.
- **AC-01.3** If a proposal has no phased plan (single monolithic change), one WI is emitted.

### US-02 — As a framework maintainer, I want the audit trail preserved when a proposal is promoted

**Why:** without it, future sessions cannot reconstruct "which WIs came from which proposal."

- **AC-02.1** The source proposal file moves to `proposals/done/<basename>.md`.
- **AC-02.2** The moved file gains a trailer appended at end-of-file: `**Promoted to:** docs/specs/work-items/WI-NNN.md, docs/specs/work-items/WI-NNN+1.md, …` (one line listing every emitted WI).
- **AC-02.3** `.svc/pipeline-decisions.jsonl` receives one new line of type `taste` with fields `{timestamp, skill: "capture-idea", mode: "from-proposal", proposal: <path>, emitted_wis: [list], reason: <one-line>}`.

### US-03 — As any user of the framework, I want no regression in the existing `capture-idea` intake behavior

**Why:** additive change must not break the primary frictionless-intake mode.

- **AC-03.1** Invoking `capture-idea` without `--from-proposal` on unstructured text produces the same WI shape as before (Goal / Context / Hypothesized Value / Broad Scope / Persona Fit / Similar Items / optional Product-Grounded Assessment).
- **AC-03.2** All existing `capture-idea` triggering prompts in `test-framework/evals/tier-1.5/prompts/` continue to match.
- **AC-03.3** `bash scripts/lint-skills-manifest.mjs` passes; `capture-idea` stays in `includedSkills`.

### US-04 — As a reviewer, I want deterministic parser behavior so proposal → WI is reproducible

**Why:** non-deterministic parsing would re-introduce the drift the seam is supposed to close.

- **AC-04.1** The parser splits on ATX headings (`## `), case-insensitive match on known block names (`Goals`, `Non-Goals`, `Acceptance Criteria`, `Scope boundary`, `File Impact`, `Rollback`).
- **AC-04.2** Phased proposals are detected by heading pattern `### Phase N — …` or `##### P<N>.<M> — …`. Each leaf becomes one WI.
- **AC-04.3** If a leaf has no AC block of its own, the phase-level AC block is inherited; if neither exists, the emitted WI carries `## Acceptance Criteria\n\n_TBD — defer to plan-changeset_`.
- **AC-04.4** WI number is derived as: highest existing `docs/specs/work-items/WI-*.md` integer + 1, counted before emission; subsequent WIs in the same invocation increment monotonically.
- **AC-04.5** Running the mode twice on the same proposal is idempotent — if the proposal is already in `proposals/done/` with a `Promoted to:` trailer, re-invocation exits with a clear "already promoted" message and does NOT create duplicates.
