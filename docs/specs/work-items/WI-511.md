# WI-511: Quality-preserving stale loop-state lifecycle

**Type:** framework maintenance

## Problem

The loop guard correctly isolates concurrent host sessions into separate gitignored files, but it never retires state from sessions that have been inactive for more than seven days. Long-lived worktrees therefore accumulate bounded-size but permanently orphaned files.

The supplied optimization bundle also proposes changes to candidate formats, SQLite retry semantics, receipt caching, timestamp validation, payload equality, and task-graph paths. Those are not presumed safe. WI-511 implements only the independently evidenced lifecycle gap and records why the other suggestions are excluded.

## Scope

### In scope

- Best-effort discovery and removal of expired loop-guard session files.
- Creator-owned lifecycle behavior inside `hooks/svc-loop-guard.mjs`.
- Hermetic Tier-1 fixtures for target selection and fail-open cleanup errors.
- Framework state, proposal, plan, review, audit, and promoted replay evidence.

### Out of scope

- Candidate reservoir input/schema changes.
- Receipt validation caching or worker architecture changes.
- Phase-receipt timestamp/equality semantics.
- Task-graph authority or persisted evidence-path format changes.
- Customer data, network APIs, UI, deployment, and background daemons.

## Invariants

1. Loop detection behavior for the current session is byte-for-byte unchanged apart from best-effort stale-file cleanup.
2. Cleanup never targets the current state file, symlinks, directories, non-matching names, or files at/inside the seven-day boundary.
3. Cleanup failure is non-fatal because stale-state retirement is maintenance, not enforcement authority.
4. State resolution remains repository/worktree scoped through `resolveSvcStateDir`.
5. No candidate, receipt, reconcile, completed-task-integrity, or task-graph contract is weakened.
6. No tracked audit history is deleted or rewritten.

## Event Contract

No new external event or persisted schema is introduced. On each non-exempt hook call:

```text
resolve scoped .svc
  -> identify current session state path
  -> best-effort prune eligible expired siblings
  -> load/update/save current state
  -> emit the same allow/warn/deny behavior as before
```

## Feature Toggle

No toggle is added. Cleanup is bounded, local, and fail-open; rollback is a code revert. Adding a toggle would create more persistent state than the cleanup removes.

## Explicitly Rejected Bundle Items

| Proposal | Disposition | Reason |
|---|---|---|
| Markdown candidate ingestion | reject | Introduces an undefined second authoritative mirror format and parser ambiguity; WI-508 deliberately chose deterministic JSON. |
| Cache `project_id` | reject | It is already resolved once per one-shot CLI process, so an in-process cache removes no subprocess. |
| Broaden candidate IDs | defer | This is a data-contract feature, not a performance optimization; it needs collision/canonicalization requirements and a separate WI. |
| Add transaction retries | reject as proposed | Existing SQLite `busy_timeout=5000` already provides bounded contention handling; stacking five retries can multiply latency and transaction re-execution risk. |
| Replace receipt workers with one Git log | reject | WI-509 deliberately uses isolated, timeout-bounded per-SHA workers and already enumerates the range once. |
| SHA-only reconcile cache | reject | Git notes and policy can change without changing the commit SHA, so SHA-only memoization can reuse stale false-green results. |
| Replace strict timestamp validation with `Date.parse()` | reject | V8 normalizes calendar-invalid timestamps; current code intentionally validates calendar and offset ranges before parsing. |
| Hash phase-receipt payload equality | reject | Exact structural equality is collision-free and canonicalization-free; hashing adds failure modes without measured benefit. |
| Store generic workspace-relative graph paths | reject | Evidence paths are already relative where required; canonical absolute worktree roots remain an authority boundary, not portable content. |
| Prune from `task-graph.mjs` | modify | Cleanup is accepted only in the loop guard that owns the state lifecycle. |

- Cleanup scope cannot be proven to exclude tracked/durable state.

## Technical Design

### Architecture

Add one internal lifecycle helper under `hooks/lib/` and invoke it from the loop guard before loading current session state. The helper owns filename filtering, cadence, cutoff, file-type refusal, and lock-aware deletion. No other hook, task graph, database, receipt validator, or state schema changes.

```text
PreToolUse payload
      |
      v
resolve repository .svc
      |
      v
derive current state path
      |
      +--> current missing/inactive >=24h? -- no --> load/update/save current state
      |
      yes
      |
      v
list exact loop-state siblings
      |
      v
exclude current / non-file / symlink / age >= cutoff / locked
      |
      v
best-effort unlink eligible stale file
      |
      v
load/update/save current state and emit unchanged decision
```

### Components

| Component | Type | Responsibility | Change |
|---|---|---|---|
| `hooks/lib/loop-guard-state-lifecycle.mjs` | internal helper | Decide scan cadence and remove only lock-safe expired loop-state files. | new |
| `hooks/svc-loop-guard.mjs` | PreToolUse hook | Invoke maintenance at the owner boundary, then preserve current detection flow. | modify |
| `test-framework/evals/tier-1/validate-loop-guard-state-lifecycle.sh` | focused validator | Prove target selection, concurrency refusal, failure tolerance, and current hook behavior. | new |

### State Machine

```text
candidate
  |-- name mismatch ------------------> preserve
  |-- current path --------------------> preserve
  |-- symlink/directory/non-regular ---> preserve
  |-- mtime >= cutoff -----------------> preserve
  |-- lock unavailable ----------------> preserve
  `-- regular + stale + lock acquired -> unlink
                                      |-- error -> preserve/continue
                                      `-- success -> removed
```

### Data Model

No schema change. Existing loop-state JSON is read and written unchanged. Filesystem `mtime` is lifecycle metadata, not business or audit data.

### Technology Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Lifecycle owner | loop guard + internal helper | The creator/consumer has the complete target namespace and runs without task-graph dependency. |
| Concurrency | existing `withStateLock`, zero-wait cleanup | Active writers win; maintenance never blocks enforcement. |
| Cadence | current file absent or inactive for 24h | Avoid a directory scan on every hot-path tool event. |
| Per-pass work | rotating batch of at most 32 regular candidate names | Bound synchronous metadata, lock, and unlink work while retiring the remaining backlog on later cadence windows. |
| Cutoff | strict `mtime < now - 7d` | Matches user requirement and preserves the exact boundary. |
| Failure mode | cleanup fail-open, loop detection unchanged | Orphan cleanup is maintenance, while loop detection is the behavioral contract. |

### Cost Model

| Dimension | Unit cost | Expected volume | Monthly estimate | Scaling curve | Paid by |
|---|---|---|---|---|---|

| Directory scan | at most once per new/inactive session day | usually tens of `.svc` entries | $0 | linear with `.svc` entry count only at cadence boundary |
| Storage | removes expired files; adds no cache | bounded JSON files | $0 | decreases abandoned-file count |

### Risks and Trade-offs

| Risk | Impact | Mitigation |
|---|---|---|
| Cleanup races an active sibling | state loss | acquire the sibling's canonical state lock with zero wait; skip on contention |
| Symlink/path trick | unintended target | exact basename in resolved `.svc`, `Dirent` + `lstat`, no recursion |
| Scan adds latency | slower tool calls | scan only for absent/inactive current state; inspect at most 32 candidate files per pass; benchmark |
| Cleanup error affects hook | enforcement regression | catch per scan/file and continue existing logic |

| Chose | Over | Rationale |
|---|---|---|
| creator-owned helper | task-graph cleanup | correct lifecycle ownership and full invocation coverage |
| no correctness cache | reconcile SHA memoization | avoids invalidation/freshness risk |
| strict existing validation | permissive parsing/hashing | no measured bottleneck justifies weaker semantics |
