# WI-321: Builder-profile-aware work item prioritization

**Type:** enabler
**Status:** backlog
**Severity:** medium
**Filed:** 2026-05-11
**Source:** OPEN-PROPOSALS.md FP-018
**Lane:** framework
**Related:** WI-104, WI-247, WI-280

---

## Problem

The framework can list or score work items without recognizing that some WIs directly address the builder's stated blocker, while others are distractions. This causes backlog prioritization to bury distribution/revenue-gap fixes and can misapply demand-evidence penalties to features that are themselves the demand-generation mechanism.

## Evidence

- `OPEN-PROPOSALS.md` FP-018
- `OPEN-PROPOSALS.md` FP-020

## Acceptance Criteria

- [ ] `list-work-items` or a routing helper reads builder-profile context when ranking WIs.
- [ ] Work items that directly address a stated builder blocker are surfaced and labeled.
- [ ] Validate-feature K1 handling distinguishes vanity features from features that solve the proof-of-demand gap.
- [ ] Add a fixture using the WI-089/WI-090 class described in OPEN-PROPOSALS.
- [ ] Output remains compact and does not regress list-work-items readability.

## Route Recommendation

Run through improve-framework. This likely touches list-work-items, validate-feature, and builder-profile references.
