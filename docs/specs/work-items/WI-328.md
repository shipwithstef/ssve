## Problem

WI-310 added the parallel wave planner and merge-back validator, but the worker
runtime still leaves several proposal requirements as contracts instead of
mechanical behavior. `dispatch-worker.sh` does not yet produce
`.svc/dispatch/<WI>.result.json`, filter Stop-hook checks by worker WI, roll up
worker edit lists for consolidated quality checks, assign shared test streams,
or emit wave progress.

## Acceptance Criteria

- [x] `dispatch-worker.sh` or a dedicated wrapper writes validated
      `.svc/dispatch/<WI>.result.json` for success and failure paths.
- [x] Worker sessions can set `SVC_WORKER_WI=<WI-id>` and Stop-hook completion
      checks only consider that WI and direct children.
- [x] Worker edit accumulators roll up to the orchestrator so consolidated
      stop-quality covers all worker changes once per wave.
- [x] Worker quality behavior is explicit: either per-worker quality runs or
      `SVC_SKIP_WORKER_QUALITY=1` is paired with mandatory orchestrator rollup.
- [x] Shared runtime resources are assigned or serialized, including Base44
      `TEST_STREAM` pools and browser/browse-daemon contention.
- [x] Timeout, non-zero exit, dirty worktree, missing result, and resume paths
      are implemented and replay-tested.
- [x] A wave progress stream or equivalent status artifact updates while
      long-running workers are active.

## Notes

This WI is runtime hardening for the already-landed wave planner. It should not
reopen the WI-310 planner or merge-back validator unless the runtime wiring
requires schema changes.
