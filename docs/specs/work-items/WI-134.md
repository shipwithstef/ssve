# WI-134: SessionStart self-heal misses dead host-install symlinks when worktree was the source

**Type:** bugfix
**Status:** VERIFIED
**Closed:** 2026-04-29
**Promoted as:** PR #52, squash-merged 2026-04-29 as commit `9d7217a`
**Confidence tier:** VERIFIED-L1 — full structural + V2 live verification (AC-06 fresh-host smoke executed against live install on the merged main commit; observed `[svc-session-start] self-heal: repaired (setup exit=0)` with no WARN line; post-state pointers + scripts symlink restored to canonical)
**Severity:** high
**Filed:** 2026-04-27
**Source:** Promotion of `proposals/2026-04-26-source-repo-pointer-must-be-canonical-not-worktree.md` — filed today after 2nd recurrence in `example-marketplace` repo (76 dead symlinks under `~/.claude/skills/`, healthcheck did not fire).
**Lane:** framework

## Symptom

Fresh `example-marketplace` session 2026-04-26: `~/.claude/skills/` contained 76 dead symlinks plus broken `hooks/` and `scripts/` symlinks. The SessionStart healthcheck (`hooks/svc-session-start-healthcheck.mjs`) did NOT self-heal. User had to interrupt twice while the agent manually re-symlinked one batch at a time.

This is the 5th recurrence of the worktree-deletion symlink-rot family (WI-079, WI-080, WI-116, WI-124 each addressed instances; the underlying defect remains).

## Root cause (verified live in source proposal)

`detectRepoRoot()` in the healthcheck has two strategies, both of which can land on a deleted worktree path:

1. Read `~/.claude/skills/.source-repo` — if that pointer was written by `setup --host claude` from inside a worktree, it points at the worktree, not the canonical repo. When the worktree is later removed, the pointer is stale and `existsSync(${p}/setup)` returns false, but the healthcheck doesn't fall back cleanly.
2. Walk up from `process.cwd()` — same risk if the SessionStart fires from inside a worktree.

WI-124 added "self-heal stale host-install symlinks" but the healthcheck still trusts `.source-repo` blindly when it exists; it doesn't validate that the path is the *canonical* repo (i.e., not under `worktrees/`).

## Fix direction

1. `setup --host <h>` MUST refuse to write `.source-repo` if `pwd` is under a `worktrees/` directory; instead resolve to the canonical repo (parent of `worktrees/`) and write that.
2. SessionStart healthcheck `detectRepoRoot()` MUST treat any `.source-repo` value containing `/worktrees/` as suspect: try the canonical-parent-of-worktrees path first, fall back to the recorded value only if the canonical path is also missing.
3. Add tier-1 validator `validate-source-repo-pointer.sh` that fails if `~/.claude/skills/.source-repo` resolves to a worktree path.

## ACs

- AC-01 — Reproduce: create worktree, run `setup --host claude` from inside it, delete the worktree, open a new Claude Code session, observe the healthcheck failure.
- AC-02 — `setup` rewrites or refuses to write a worktree-pathed `.source-repo`.
- AC-03 — Healthcheck `detectRepoRoot()` recovers when `.source-repo` points at a deleted worktree path.
- AC-04 — Tier-1 validator catches the bad pointer before it bites.
- AC-05 — After fix, deliberately stale `.source-repo` self-heals on next SessionStart with no manual intervention.

## Why high severity

This blocks every fresh session in any repo that ever ran `setup` from a worktree. The user's words: "next session in any host repo, the SessionStart hook silently self-heals" — that promise is unmet five WIs running. Each recurrence costs ~15 min of manual symlink repair before any real work starts.

## Out of scope

- Restructuring how worktrees relate to the canonical repo (beyond what `setup` already assumes).
- Migrating the healthcheck to a different language/framework.

### Root cause

- **Immediate cause:** `detectRepoRoot()` returns `null` when both Strategy 1 and Strategy 2 inputs (`.source-repo` and `scripts/` symlink target) resolve to a deleted-worktree path. The function has no terminal fallback.
- **Enabling condition:** Pre-2026-04-25 installs, or any post-2026-04-25 install run with `SVC_SETUP_ALLOW_WORKTREE=1`, bind every symlink under `~/.claude/skills/` to one shared ephemeral path. When that worktree is removed, every pointer dies simultaneously, defeating WI-124's "at least one pointer survives" assumption.
- **Why the system allowed it:** WI-124's self-heal design only added repair-via-setup *after* `detectRepoRoot` returned a path. It assumed at least one of the two pointers would survive worktree cleanup. The single-shared-ephemeral-path failure mode wasn't in the test matrix.

### Learnings

**Rule candidate** (file as `rules/framework/install-pointer-resilience.md` if this fires twice more):

> Long-lived install pointers (paths persisted into `~/.claude/skills/.source-repo`, hook-command paths in host settings, hook-script paths in MCP configs) MUST have a terminal recovery strategy that does not depend on any prior pointer surviving. The recovery strategy MUST filter out `.worktrees/` substrings before accepting a candidate, OR the install MUST refuse to write a worktree-pathed pointer in the first place. Both layers — write-time guard AND read-time fallback — are required; either alone is insufficient (the bypass exists; pre-existing broken installs cannot be retroactively fixed by write-time guards).

**Why:** WI-079, WI-080, WI-116, WI-124 each treated "stale symlink" as the bug. The structural bug is "install address-of-source bound to ephemeral path AND no terminal fallback in the read side." The write-time guard (commit 52ef4eb) closes the inflow. Strategy 3 closes the outflow. Anything less than both leaves a recurring failure mode.
