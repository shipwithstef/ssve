# WI-499: Codex session-id bridge + SessionStart JSON host-contract

**Type:** bugfix (Codex host-contract; enforcer ownership resolution)
**Status:** identified
**Severity:** high — without these, EVERY governed Codex mutation is denied ("no owned in_progress task"), and every Codex session start reports "invalid session start JSON output". Blocked real Codex work for ~4 days.
**Filed:** 2026-07-19
**Source:** owner — live Codex sessions in onboarded repos (example-marketplace) blocked past WI-498's deadlock fix. Root-caused live, hot-patched, and proven: after deploying the session-id bridge, a Codex session autonomously built + shipped the entire Social Favourites feature (example-marketplace PR #293).
**Lane:** framework
**Related:** WI-486/494/496/498 (Codex governance chain). This is the missing piece that made them actually usable on live Codex.

## Problem

**D1 — enforcer ownership resolution reads the session id from the ENVIRONMENT, but live Codex passes it in the PAYLOAD.** The enforcer's `sessionId(payload, env)` correctly reads `payload.session_id`, but ownership resolution (`activeTask -> laneGraphs -> resolveWI({cwd}, env)`) reads the session id from `env` only. Live Codex sets the session id in the stdin payload, NOT the process environment — so `resolveWI` sees no session, finds no owned graph, and denies EVERY governed mutation with "no owned in_progress task". Every isolated test passed only because the tester set `SVC_SESSION_ID` in env by hand; the live path never does. (Proven: A/B — payload-only session DENY, env session ALLOW.)

**D2 — SessionStart hooks emit non-JSON, which Codex rejects.** `svc-learning-preload.mjs` prints plain-text learnings and `svc-session-start-healthcheck.mjs` exits with empty stdout. Claude Code accepts plain-text SessionStart stdout as added context; Codex REQUIRES valid JSON and reports "hook returned invalid session start JSON output". Cosmetic (the hooks still run their side-effects) but noisy and alarming every session start.

## Fix

**D1 (`hooks/codex/svc-codex-skill-load-enforcer.mjs`):** before ownership resolution, bridge the payload-derived `ctx.session_id` into `process.env.CODEX_SESSION_ID` — but only when the env carries NO session id (never overriding a real env/CI/test session). `ctx.session_id` comes from the trusted `hookContext`, so this is safe. Resolution then finds the owned graph and authorizes correctly.

**D2 (`hooks/svc-learning-preload.mjs`, `hooks/svc-session-start-healthcheck.mjs`):** detect the host from the literal invocation path (`argv[1]` under `~/.codex/` => Codex; the spawned self-check probe uses `argv[1]="-"` and is excluded). On Codex, emit valid JSON — the learnings wrapped in the `{hookSpecificOutput:{hookEventName:"SessionStart",additionalContext}}` envelope, or `{}` when there is nothing. Claude output is byte-identical (plain text) — zero Claude behavior change.

## Acceptance criteria

- [ ] SB-01: with the session id ONLY in the payload (no env), the enforcer AUTHORIZES the loader/governed mutation for the owned graph (was DENY). Env session still authorizes; a session that owns nothing is still denied.
- [ ] SB-02: the env-bridge never overrides an existing `SVC_SESSION_ID`/`CODEX_THREAD_ID`/`CODEX_SESSION_ID`.
- [ ] SB-03: both SessionStart hooks emit VALID JSON when invoked via a `~/.codex/` path; Claude-path output is byte-identical plain text.
- [ ] SB-04: `node --check` clean on all three files; tier-1 green.
- [ ] SB-05: live proof — a Codex session governs+builds end-to-end (already demonstrated: example-marketplace PR #293).
