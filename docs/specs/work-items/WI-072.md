## Problem

`hooks/svc-workflow-guard.js` is the last major svc hook still using CommonJS (`require`) and ad-hoc payload extraction. The shared libraries `hooks/lib/hook-payload.mjs` and `hooks/lib/hook-decision.mjs` exist (created 2026-04-23 / 04-24 session) but this hook can't consume them without an ES-module port.

Direct consequences:

- `svc-workflow-guard.js` duplicates stdin-reading and tool-input extraction logic that already lives in `hook-payload.mjs`. Divergence risk: the shared lib gets fixes (e.g., new host envelope variants) that the guard doesn't pick up.
- `svc-workflow-guard.js` writes decisions via bespoke `console.log` / `process.stderr.write` / `process.exit` calls instead of the shared `hook-decision.mjs` serializer. This means its outputs don't get host-aware formatting (the `permissionDecision` modern schema on Claude/Kimi/Codex, the `{decision:"deny"}` shape on Gemini).
- The same pattern applies to `hooks/svc-lane-tasks-validator.mjs`, `hooks/svc-lane-tasks-failure.mjs`, and `scripts/eval-gate.mjs` — all currently stdin-first but with their own extraction functions, not consuming `hook-payload.mjs`. Same divergence risk.

Under the adopted plan-changeset-trigger rule (`rules/plan-changeset-trigger.md`), this is a **refactor-without-behavior-change AND hot-path edit** — both signals fire. Requires disciplined execution.

## Goals

1. `hooks/svc-workflow-guard.js` → `hooks/svc-workflow-guard.mjs`; consume `hook-payload.mjs` + `hook-decision.mjs`.

## User Stories

### US-01 — As a framework maintainer, I want workflow-guard to share the same payload extractor as loop-guard

**Why:** divergence between two extractors is a known failure mode (the stdin-vs-argv bug I fixed 2026-04-23 had to be fixed in both files separately).

**AC-01.1** — `hooks/svc-workflow-guard.mjs` imports `readHookPayload` from `./lib/hook-payload.mjs` and does not declare its own `parseInput` or `extractCommand`/`extractFilePath` helpers (may still have thin wrappers over the shared `extractCommand`/`extractFilePath` helpers in `hook-payload.mjs`).

**AC-01.2** — Running the hook with any of the 4 host envelope shapes (Claude, Kimi, Codex, Gemini payloads) correctly extracts `tool_name`, `tool_input.file_path`, `tool_input.command` and reaches the correct code branch (--edit-write / --phase-boundary / --bash-guard).

### US-02 — As a framework maintainer, I want workflow-guard to emit decisions via the shared serializer

**Why:** Gemini's strict pure-stdout contract means even one stray `console.log` breaks the hook. Today `svc-workflow-guard.js` writes warnings via `process.stderr.write` (correct) and errors via `process.stderr.write` + `process.exit(1)` (wrong — exit 1 is undefined on all 4 hosts; exit 2 is the universal contract).

**AC-02.1** — Hard blocks go through `blockViaExit(reason)` (stderr + exit 2) from `hook-decision.mjs`.

**AC-02.2** — No call sites remain that use raw `process.exit(1)` — that exit code is not documented in any host's hook contract.

**AC-02.3** — Soft warnings still use `process.stderr.write` directly (no decision emit needed for warnings).

### US-03 — As a framework maintainer, I want the three other stdin-reading hooks to converge on the shared extractor

**AC-03.1** — `hooks/svc-lane-tasks-validator.mjs`, `hooks/svc-lane-tasks-failure.mjs`, `scripts/eval-gate.mjs` all call `readHookPayload()` as their sole input extraction path.

**AC-03.2** — Their existing inline `_readStdin` / `_stdin` / `_argv` helpers are removed.

### US-04 — As any user of the framework, I want no regression in guard behavior

**AC-04.1** — `tier-1/validate-loop-guard.sh` continues to PASS 11/11 (proves hook-payload.mjs didn't break).

**AC-04.2** — A new tier-1 test `validate-workflow-guard.sh` exercises all three modes (default, `--phase-boundary`, `--bash-guard`) against fixture payloads covering each of the 4 host envelope shapes. 15+ cases, all pass.

**AC-04.3** — `tier-1/validate-claude-hook-e2e.sh` continues to PASS (end-to-end regression).
