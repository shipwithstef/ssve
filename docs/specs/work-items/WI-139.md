# WI-139: landing-page + benchmark-landing must run mandatory visual side-by-side before declaring done

**Type:** bugfix
**Status:** VERIFIED
**Severity:** high
**Filed:** 2026-04-29
**Source:** Promoted from `proposals/2026-04-28-landing-skill-mandatory-visual-side-by-side.md`. Filed after Example Marketplace WI-088 iter1 + WI-161 both shipped landing iterations with self-graded PASS while the live page visually fell far short of named sector anchors. User caught both post-ship. Two recurrences with same signature = pattern, not incident.
**Lane:** framework

## Symptom

Landing-page work declares "done" via textual/contractual checks (bundle-grep ✅, lane-tasks 5/5 ✅, perf budget ✅, gap "closed" via CSS-only mocks) while the shipped result visually fails against the very anchor bank the framework already maintains. No automated check or skill output ever rendered the shipped page next to the benchmark anchor at the same scale.

## Root causes

1. `benchmark-landing` is **text-graded**, not visually-graded. Its 8-dimension rubric is filled by introspection; the skill never renders both pages.
2. `verify-promotion` for landing-tagged WIs accepts bundle-grep as evidence — a string can ship without the section *looking* like the anchor.
3. No "would you ship this against $ANCHOR" gate. Self-Verify checks contracts and presence, not aesthetic parity.
4. Below-fold gap closure has no visual receipt. CSS-only mocks pass text checks while occupying ~3% of the visual real estate of an anchor's product screenshot section.
5. The framework knew about Toast (WI-158 anchor bank) as the benchmark and never compared to it. The 21-anchor bank was used for capture and gap analysis but never for **visual comparison of the shipped result**.

## Fix direction

Three additive changes + 1 validator. Leverage existing `track-visuals` skill (Playwright-backed) rather than reimplementing rendering in each skill.

### A. `benchmark-landing` skill — Step 0 mandatory visual side-by-side

Before scoring any dimension:
1. Render the target page at 1440×900 full-page screenshot
2. Render top-2 sector anchors + top-1 high-performer from `landing-bank/` at the same size
3. Save a stitched 4-up comparison image to `docs/specs/landing/<wi>-side-by-side.jpg`
4. Refuse to score until that artifact exists
5. Verdict report must include path + an honest one-line aesthetic judgment per anchor ("matches density / falls 30% short / falls 60% short")
6. If side-by-side shows page is visually thin (>40% more white space than median anchor, or product UI section <50% height of anchor's equivalent), cap below-fold-density at 4/10 regardless of textual checklist completion.

### B. `verify-promotion` — landing-tagged WIs require visual receipt

For any WI tagged `landing` / `marketing-page`:
1. Re-run side-by-side after deploy (live URL, not local build)
2. Diff against pre-implementation side-by-side stored at WI start
3. Require: shipped change is visible in production at comparison scale (not just present in bundle string)
4. Include post-deploy screenshot in WI's verify-promotion receipt

### C. `landing-page` skill — Step 0.5 ship-readiness gate

After Market-Gap analysis, emit binary: "ship-ready vs $ANCHOR_TOP_1" yes/no with one-paragraph honest read of visual gap. This becomes the load-bearing question for any downstream landing WI: does the proposed change actually close visual parity with the named benchmark, or is it cosmetic?

### D. New tier-1 validator

`test-framework/evals/tier-1/validate-landing-side-by-side-exists.sh` — for every WI tagged landing/marketing-page with status VERIFIED, asserts the side-by-side artifact exists at `docs/specs/landing/<wi>-side-by-side.jpg`.

## ACs

- AC-01 — `benchmark-landing` refuses to score if `docs/specs/landing/<wi>-side-by-side.jpg` is missing; emits explicit "render side-by-side first" error with the exact command needed.
- AC-02 — `benchmark-landing` verdict output includes side-by-side artifact path AND honest aesthetic judgment line per anchor.
- AC-03 — When side-by-side shows visual thinness (>40% more white space than median anchor, or product UI height <50% of anchor's), `below-fold-density` score is capped at 4/10 regardless of textual completion.
- AC-04 — `verify-promotion` for any WI tagged landing/marketing-page captures a post-deploy live-URL side-by-side, diffs against pre-implementation, requires the change to be visible at comparison scale.
- AC-05 — `landing-page` Step 0.5 emits binary ship-ready vs $ANCHOR_TOP_1 with one-paragraph honest gap read, surfaced in the WI's lane-tasks receipt.
- AC-06 — Tier-1 validator `validate-landing-side-by-side-exists.sh` exists; iterates landing/marketing-tagged WIs in VERIFIED state, exits non-zero if any side-by-side artifact missing.
- AC-07 — Existing `track-visuals` skill is reused (not re-implemented). Where benchmark-landing/verify-promotion/landing-page need rendering, they invoke track-visuals with appropriate parameters; the side-by-side stitcher is a thin wrapper over track-visuals output.
- AC-08 — Schema for the side-by-side artifact is documented (image dimensions, anchor selection rule, stitching layout) so all three calling skills produce identical-shape output.

## Why high severity

Two recurrences with same signature (Example Marketplace WI-088 iter1, WI-161) where landing iterations shipped self-graded PASS while user caught visual thinness on first inspection. Per `rules/learning-preload.md` learning-to-rule promotion threshold: pattern, not incident. Lost-credibility cost is high; fix cost is bounded (~half-day given track-visuals already exists).

## Out of scope

- Reimplementing Playwright rendering in any skill (use existing track-visuals)
- Auto-fixing visually-thin pages (this WI gates ship; remediation stays in landing-page skill's existing flow)
- Mobile viewport side-by-side (1440×900 desktop only for v1; mobile is a follow-up)
- LLM-as-judge aesthetic scoring (the honest-judgment line is human-authored or one-shot Sonnet — not part of an automated rubric)
