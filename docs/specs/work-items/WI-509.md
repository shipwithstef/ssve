# WI-509: Bound receipt-range validation without false reconcile debt

**Type:** bugfix
**Status:** VERIFIED-L3
**Confidence:** L3 — headless promoted CLI and reconciliation replay
**Severity:** high
**Filed:** 2026-07-23
**Source:** diagnose-bug follow-up to WI-472
**Lane:** framework
**Related:** WI-472, WI-498, WI-508

## Problem

`scripts/svc-reconcile.mjs` gives its receipt child at most 20 seconds, but
`scripts/check-chain-receipts.mjs --range` validates every commit sequentially.
The current 166-commit checkpoint interval needs about 90 seconds, so reconcile
reports every commit as missing because the child timed out even though the
receipt set is complete. This blocks every governed workflow from creating its
worktree.

## Reproduction

- **Trigger:** Run `SVC_RECONCILE_CHILD_TIMEOUT_MS=20000 node scripts/svc-reconcile.mjs`
  from the default checkout whose checkpoint starts at
  `985a8d5de2255288daaacda91c739e294b8a67d5`.
- **Expected:** The bounded receipt-range child validates the interval, reports
  zero unaccounted commits, and lets reconcile advance the checkpoint.
- **Actual:** The child reaches 20 seconds, reconcile exits 1, and all 166
  commits are projected as `missing receipt check timeout`.
- **Causal classification:** Action bug. Reconcile itself cannot complete its
  required receipt-validation action inside its declared bound.
- **Bug domain:** Code. The same notes, checkpoint, and commit interval pass
  when the receipt validator is allowed to finish.

## Evidence

- Four canonical reconcile attempts timed out at 10 or 20 seconds.
- The exact underlying command,
  `node scripts/check-chain-receipts.mjs --range 985a8d5d..origin/main`,
  completed successfully with all 166 commits valid.
- Sequential range validation took roughly 90 seconds.
- A read-only eight-worker replay of the same per-SHA validations completed in
  8.18 seconds; a twelve-worker replay completed in 7.22 seconds.
- `scripts/check-chain-receipts.mjs` currently ends range mode with
  `shas.map(checkSha)`, while each `checkSha` performs synchronous Git and
  receipt-integrity work.

## Expected Behavior

Range mode must preserve the same fail-closed result for every SHA while using a
bounded worker pool so the current receipt interval finishes within reconcile's
20-second child limit. Direct single-SHA mode must remain unchanged.

## Root Cause

- **Immediate cause:** Range mode validates all SHAs serially.
- **Enabling condition:** The checkpoint interval grew from the 78-SHA WI-472
  validation set to 166 SHAs, making per-SHA synchronous Git work cumulative.
- **Systemic cause:** WI-472 proved that reconcile invoked one range child, but
  its focused fixtures mocked that child and did not enforce range-validator
  latency as history grew.

## Smallest Safe Fix

Add a bounded, deterministic worker pool for multi-SHA range validation inside
`scripts/check-chain-receipts.mjs`. Each worker invokes the self-located
validator in direct `--sha` mode; results are stored by input index, so output
ordering and fail-closed semantics remain stable. Cap concurrency and per-worker
time, preserve direct `--sha` behavior, and add hermetic success/failure/order
fixtures plus a live-range performance replay.

## Pattern Scan

receipt slot, and Tier-1 receipt-schema scans.

`shas.map(checkSha)` loop. Single-SHA callers are not affected. A separate
receipt-schema validator slowdown is already documented in WI-505 evidence and
is not coupled to this range worker pool.

## Learnings

A bounded parent process is not sufficient when one child performs unbounded
serial work proportional to repository history. Performance gates must exercise
the real growing denominator and preserve fail-closed per-item attribution.
