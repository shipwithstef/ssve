# WI-143: refresh-competitors skill + raise competitor floor to 30 + analyze-competitors split

**Type:** framework
**Status:** VERIFIED
**Severity:** medium
**Filed:** 2026-05-02
**Source:** Deferred slice of `proposals/2026-05-02-competitive-grounding-as-default.md`. Bundled changes pulled out of WI-142 to keep that WI single-axis (gate-read path).
**Lane:** framework
**Blocked-by:** WI-142 (knowledge-base read path must exist before refresh writes against it)

## Symptom

Once WI-142 lands and the gate reads from `references/knowledge/competitors/<slug>/`, three follow-ups become tractable but were intentionally NOT bundled:

1. **No async refresh** — knowledge base goes stale without an out-of-band mechanism. Gate reads stale data → grounding decays.
2. **Competitor floor too low** — current `analyze-competitors` caps at ~20 across 4 tiers. Real industry baselines need ~30 (8-10 direct, 8-10 adjacent, 6-8 emerging, 4-6 macro). 4-6 direct competitors miss 90th-percentile patterns.
3. **`analyze-competitors` conflates two operations** — comprehensive one-shot per-competitor (when adding to tracked set) vs scheduled diff (when refreshing existing set). Same skill, different cost profile, different cadence.

## Fix direction

Three changes after WI-142 lands:

### A. New `refresh-competitors` skill

- Diff-based, runs against tracked competitor set
- For each tracked competitor: WebSearch homepage + pricing page + recent press, diff against `references/knowledge/competitors/<slug>/.last_known_state.json`
- If diff detected: append to `changelog.jsonl` with what changed (price change, new feature, integration, executive change)
- If diff significant: bump confidence flag, optionally queue focused refresh of affected file (`pricing-history.md`, `earn-mechanism.md`)
- Output: per-week summary surfaced as "competitive landscape changed this week" digest
- NEVER triggers full re-analysis — that's `analyze-competitors` for new entrants

### B. Scheduled routine

Default weekly cadence via `/schedule` agent (per-project routine in `~/.claude/routines/<project>-competitor-watch`). Uses existing `schedule` skill infrastructure. Never blocks gate latency.

### C. Raise competitor floor + retier

`analyze-competitors` 4-tier table:
- Direct: target 8-10 (was up to 6)
- Adjacent: target 8-10 (was up to 5)
- Emerging/insurgent: target 6-8 (was up to 5)
- Macro disruptors: target 4-6 (was up to 4)

Deep analysis (9 dimensions) on direct + adjacent (~16-20). Core dimensions only on emerging/macro (~10-14).

If domain genuinely has fewer competitors → `landscape_state: nascent` or `none-found` covers it, but search must be exhaustive enough to PROVE the count.

## ACs

- AC-01 — `refresh-competitors/SKILL.md` exists with declared inputs/outputs/chain. Lints pass.
- AC-02 — `refresh-competitors` writes to `references/knowledge/competitors/<slug>/changelog.jsonl` (append-only, dated). Updates `.last_known_state.json` per competitor.
- AC-03 — Scheduled routine template: `~/.claude/routines/<project>-competitor-watch` documented in `references/scheduled-routines.md`. Weekly cadence default, configurable.
- AC-04 — `analyze-competitors/SKILL.md` updated to target floor of 30 across 4 tiers. Validator `validate-competitor-floor.sh` asserts `analyze-competitors.data.json` contains ≥30 entries OR `landscape_state: nascent|none-found` is set with justification.
- AC-05 — `analyze-competitors` no longer runs as a refresh. Skill description explicitly: "comprehensive one-shot per competitor, populates knowledge base. Run when adding a competitor to tracked set."
- AC-06 — Cost-floor evidence: at least one project has run `refresh-competitors` weekly for 2 weeks; changelog shows real diffs detected; gate reads include the refreshed data.
- AC-07 — Migration: existing projects with `analyze-competitors.data.json` at <30 count get a one-time `audit-competitors-floor` advisory listing what's missing per tier.

## Why medium severity

WI-142 closes the load-bearing gap (gate ALWAYS grounds, reads from knowledge base). Without WI-143 the knowledge base goes stale, but that's a slow decay, not a sharp failure. WI-143 is the maintenance layer that keeps WI-142's grounding fresh over time.

## Dependencies

- WI-142 must land first. The `readKnowledgeBase` function and the `references/knowledge/competitors/<slug>/` directory layout are prerequisites.
- `schedule` skill (existing) must support per-project routines with weekly cadence (verify before starting).

## Cost

- New skill (~200 lines SKILL.md + scaffolding)
- 1 new validator
- 1 routine template
- `analyze-competitors` SKILL.md edit (floor change)
- Estimated: 2-3 PRs, 1 session — but should not start until WI-142 lands and runs in real projects long enough to expose any read-path issues.

## Out of scope

- Replacing `analyze-competitors` with `refresh-competitors` (they coexist — different purposes)
- Per-competitor full re-analysis on diff detection (that's manual via `analyze-competitors` rerun)
- Cross-project shared knowledge base (per-project knowledge for now)
