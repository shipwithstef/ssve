# WI-195: Atomic state writer not universally enforced; no lock/concurrent-session protection

## Problem

Atomic JSON writes ARE implemented. `scripts/state-io.mjs` provides `writeJsonAtomic()` using temp-file + fsync + rename, which is the standard atomic-write pattern.

The real gap is narrower than the original review framing:

1. **Not universally enforced.** There is no validator or lint that fails when a script writes to `.svc/orchestrator-state.json`, `.svc/lane-tasks-*.json`, `.svc/capability-registry.json`, or any other state file via `fs.writeFileSync` / `fs.writeFile` instead of `writeJsonAtomic`. New code can bypass `state-io.mjs` silently.
2. **No locking.** `state-io.mjs` performs single-writer atomicity but has no lock files, no stale-lock recovery, and no reader-writer coordination. Two concurrent agents (parallel host sessions, autorun + manual edit, two skill invocations) writing the same file race on read-modify-write — the second write clobbers the first's mutation even though each individual rename was atomic.
3. **No append-log discipline for jsonl.** `.svc/pipeline-decisions.jsonl`, `.svc/concern-hits.jsonl`, `.svc/framework-gaps.jsonl`, etc. are append-only by convention but written via raw `fs.appendFileSync`. Concurrent appends on most filesystems are atomic per `write(2)` only when the line is small enough; large entries can interleave.

The original WI title implied "no atomicity exists" which is wrong — atomicity per-write exists; the gap is universality and concurrency.

## Evidence

- `scripts/state-io.mjs:1` — atomic temp+fsync+rename writer exists
- `proposals/done/2026-04-25-dynamic-deterministic-reliability-review.md` — original review framing
- Grep across `scripts/` and `hooks/` shows several call sites still using `writeFileSync` directly on `.svc/*.json` without going through `writeJsonAtomic`

## Impact

- Parallel agents on the same project (autorun + interactive, two hosts running in parallel) can race on lane-tasks or registry mutations and silently lose updates.
- jsonl logs can interleave under concurrent append from hooks + skills, corrupting decision-log replay tools.
- New scripts bypass `writeJsonAtomic` because nothing forces them to use it.

## Proposed Fix

1. **Lint-level enforcement.** Tier-1 validator `validate-state-io-discipline.sh` greps `scripts/`, `hooks/`, and skill scripts for `writeFileSync`/`writeFile` calls whose path argument matches `.svc/*.json` and fails unless the call comes from `state-io.mjs` itself.
2. **Lock-file primitive.** Extend `state-io.mjs` with `withStateLock(filePath, fn)` using O_EXCL lock files at `<filePath>.lock`, configurable timeout, and stale-lock recovery (PID + age check).
3. **jsonl append helper.** Add `appendJsonlLine(filePath, obj)` to `state-io.mjs` that wraps the line in a single `write(2)` syscall (size-bounded) or uses an advisory lock on larger payloads.
4. **Migrate existing call sites.** Audit all `.svc/*.json` writers and route them through `state-io.mjs`.

## Acceptance Criteria

- AC1: Tier-1 validator `validate-state-io-discipline.sh` exists, runs in `run-all-evals.sh --tier1`, and fails on any direct write to `.svc/*.json` outside `state-io.mjs`.
- AC2: `withStateLock(path, fn)` is implemented in `state-io.mjs` with stale-lock recovery and a documented timeout default.
- AC3: `appendJsonlLine(path, obj)` is implemented and used by `pipeline-decisions.jsonl`, `concern-hits.jsonl`, `framework-gaps.jsonl` writers.
- AC4: All existing `.svc/*.json` writers in `scripts/`, `hooks/`, and skills now use `state-io.mjs`. Greppable proof in PR.
- AC5: A targeted concurrency replay fixture demonstrates two parallel writers no longer lose updates.
