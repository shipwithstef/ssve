# WI-300: Skill outcome contract and progressive delivery graph mutation

## Goal

Allow the graph to evolve as work unfolds without returning to model-memory orchestration. Major skills must emit machine-readable outcomes, and route-workflow must re-evaluate the graph before proceeding.

## Mutation Actions

Supported actions:

- `insert_task`
- `mark_n_a`
- `escalate_review`
- `reclassify_lane`
- `return_to_prior_gate`
- `block_until_user_input`
- `close_as_runtime_accepted`
- `close_as_corrective_closure_complete`
- `close_as_framework_complete`

Each mutation must record source skill, signal discovered, reason, affected tasks, affected evidence families, and validator proof.

## Acceptance Criteria

- AC1: A `skill_outcome` schema is documented for major skills that can add graph signals.
- AC2: `diagnose-bug`, `validate-feature`, `write-spec`, `design-tech`, `plan-changeset`, `execute-changeset`, `review-plan`, `review-gate`, `audit-implementation`, `test-journeys`, `write-e2e`, `verify-promotion`, and `audit-session-execution` declare or reference the contract.
- AC3: Graph mutation appends to `delivery_graph.mutation_history`.
- AC4: Mutation writes use the state writer and locking discipline from [WI-195](WI-195.md), which is now the required primitive for authoritative graph mutation.
- AC5: Fixtures prove a discovered browser-visible signal inserts visual evidence, a graph mismatch inserts audit-session-execution, and a contradiction returns to a prior gate.

## Dependencies

- Authoritative mutation dependency: [WI-195](WI-195.md) provides the required lock and state writer primitive.
