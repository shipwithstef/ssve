# WI-513: Enforce the `authorization_envelope` declared in the session contract

**Type:** framework improvement
**Status:** identified
**Severity:** medium
**Filed:** 2026-08-04
**Source:** WI-512 Batch 2 — proposal §4c landed DECLARATIVE ONLY; enforcement was explicitly deferred for budget
**Lane:** framework

## Problem

WI-512 landed `authorization_envelope` as a declarative field in the session contract (`_shared/session-contract.md`, referenced from `route-workflow/SKILL.md`). It states, per environment class, whether the executor may act autonomously or must ask — `staging: auto · prod: auto · live-payment: ask`, with the operative rule that **the executor stops only outside the envelope**.

Nothing enforces it. The field is currently documentation: an executor that ignores it is indistinguishable from one that honors it, and an executor that stops *inside* the envelope — the waste class §4c exists to close — is equally invisible.

The proposal's own motivation is a measured one: 83 turns in a single audited session were pure "proceed" acknowledgements, i.e. the executor stopping for permission it had already been granted. A declaration with no enforcement does not recover any of those turns.

## Scope

### In scope

- An enforcement point that reads `authorization_envelope` from the active session contract and evaluates a proposed action's environment class against it.
- Two-sided enforcement, because both failures are real: acting **outside** the envelope must be blocked, and stopping **inside** it should be surfaced as the waste it is.
- A default for contracts that declare no envelope — necessarily conservative (treat as `ask`), and explicitly documented as the fallback rather than left implicit.

### Out of scope

- Changing the envelope's schema or vocabulary as landed by WI-512.
- Any change to the receipt envelope or the review chain.

## Open design question (resolve during planning, do not assume)

There is no obvious existing hook that sees "the executor is about to take an outward-facing action" as a distinct event — which is exactly why WI-512 deferred this rather than guessing. The plan must first establish **whether such an enforcement point exists**, and if not, whether one can be added without putting a new check on the hot path. Adding a per-tool-call hook to enforce a field that is unset in most sessions would trade a documented waste class for an undocumented latency cost.

## Acceptance criteria

- [ ] **AC-1** The plan names a concrete enforcement point and cites the evidence that it actually observes the action class the envelope governs — not an approximation.
- [ ] **AC-2** An action outside the declared envelope is blocked with the standard 5-field actionable denial naming the envelope row that denied it.
- [ ] **AC-3** A stop inside the declared envelope is recorded (not blocked) so the waste class becomes measurable rather than anecdotal.
- [ ] **AC-4** A contract with no `authorization_envelope` behaves exactly as today, and the fallback is documented.
- [ ] **AC-5** Hot-path cost is measured before and after; a regression larger than the enforcement's own budget sends the design back rather than shipping.
- [ ] **AC-6** Tier-1 coverage for both the blocked-outside and recorded-stop-inside paths.
