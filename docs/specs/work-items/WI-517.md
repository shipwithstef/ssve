## Problem

OPT-16 asked whether any read-then-write sequence in `scripts/task-graph.mjs` should become `updateJsonAtomic`. The audit found real ones: `record-phase` (`scripts/task-graph.mjs:808-823`) plus the `writeGraph` sites at `:478`, `:508`, `:652`, `:686` share a single top-level read, so two concurrent invocations can each read the graph, each write it, and silently lose one update.

WI-512 stopped rather than converting, on the grounds that the closures call `die()`/`process.exit()` and `process.exit()` skips `finally`, which would leak the lock. **That mechanism is real and was verified** — but the "no bounded conversion exists" framing was refuted by the reviewer: the safe idiom already ships *in the same file* at `scripts/task-graph.mjs:710`, where `updateJsonAtomic(...)` is called with `throw new Error(...)` inside the closure and the catch outside. Converting `record-phase` that way is bounded work, not a refactor.

Stopping was defensible on diff-cap grounds. It was not defensible on impossibility, and this WI records the difference so the item is not re-deferred with the same wrong reason.

## Scope

- Convert `record-phase` to `updateJsonAtomic` using the existing `:710` throw-inside-closure idiom, so no `process.exit()` runs inside the lock.
- Assess the four `writeGraph` sites on the same basis; convert those that fit the idiom, and record why any that do not.

## Acceptance criteria

- [ ] **AC-1** No `process.exit()` executes inside any `updateJsonAtomic` closure in this file.
- [ ] **AC-2** Two concurrent `record-phase` invocations do not lose an update — demonstrated with a real concurrent test, not argued.
- [ ] **AC-3** The lock is released on every path, including the error path.
- [ ] **AC-4** Each unconverted `writeGraph` site carries a written reason.
