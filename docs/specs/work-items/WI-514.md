# WI-514: `svc-skill-artifact-authenticity` is defeated by choosing a different tool

**Type:** framework defect (guard bypass)
**Status:** identified
**Severity:** high
**Filed:** 2026-08-04
**Source:** WI-512 Batch 1 adversarial review, finding B1-003 (reproduced live during the batch, not theorized)
**Lane:** framework

## Affected Files

- `hooks/svc-skill-artifact-authenticity.mjs`, `hooks/hooks.json`, shared Bash target classification, and the focused guard-bypass validator.

## Problem

`hooks/svc-skill-artifact-authenticity.mjs` (the G-4 guard) is registered as a `PreToolUse` hook with matcher `Edit|Write`, while its protected-path table covers high-value targets exactly — `skills-manifest.json` among them. The matcher is the whole enforcement surface.

Consequence: **any Bash write to a protected path is unguarded.** `python -c`, `sed -i`, a heredoc, `jq > file`, `printf >>` — none of them are `Edit` or `Write`, so none of them are seen. The guard is not bypassed by defeating its logic; it is bypassed by picking a different tool.

This is not hypothetical. During WI-512 Batch 1 the doer hit the G-4 90-minute skill-invocation window on `skills-manifest.json`, and worked around it by writing the same insertion via Bash — successfully, and without any denial. The resulting content happened to be correct and lint-green, which is exactly what makes the class dangerous: the bypass is silent and leaves no trace distinguishable from an authorized edit.

## Why this matters more than the specific file

Every `PreToolUse` guard in the framework that declares `Edit|Write` as its matcher shares this hole. The audit should enumerate them rather than patch one. A guard whose threat model omits the most general write primitive available to the agent is providing assurance it does not have — and the false assurance is worse than no guard, because reviewers stop looking.

## Scope

### In scope

- Enumerate every `PreToolUse` hook whose matcher is `Edit|Write` (or any subset omitting `Bash`) while protecting concrete paths.
- Extend the matcher to include `Bash` with argv/heredoc path extraction, so a write to a protected path is caught regardless of the tool that performs it.
- Negative-path tier-1 coverage: a Bash write to a protected path must be denied, and the test must fail if the matcher regresses.

### Out of scope

- Changing which paths are protected, or the 90-minute skill-invocation window policy itself.
- Guards that intentionally scope to `Edit|Write` because the Bash path is separately covered — document each such exemption rather than silently leaving it.

## Prior art

`WI-501` shipped a decoded-argv read-only classifier for exactly this parsing problem (extracting real targets from a shell command line without being fooled by quoting or encoding). Reuse it; do not write a second parser.

## Acceptance criteria

- [ ] **AC-1** Every `PreToolUse` guard protecting concrete paths is enumerated with its current matcher, and each is either extended to cover `Bash` or carries a written exemption naming what else covers it.
- [ ] **AC-2** A Bash write (`python -c`, `sed -i`, heredoc, and `jq >` forms at minimum) to a protected path is denied with the standard 5-field actionable denial.
- [ ] **AC-3** Path extraction reuses the WI-501 decoded-argv classifier rather than a new parser.
- [ ] **AC-4** Tier-1 negative coverage fails if the matcher is narrowed back.
- [ ] **AC-5** No false denials on Bash commands that only read protected paths.

## Notes

Filed from WI-512 rather than fixed inside it: the finding is real and reproduced, but fixing it is a hot-path hook change that deserves its own chain run rather than a ride-along in a lightweight-mode batch whose tests are disabled.
