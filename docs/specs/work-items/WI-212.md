# WI-212: Phase-receipts Phase C — rolling backlog of skill migrations

## Goal

After Phase B (WI-211) migrates the canonical 5 skills, migrate the remaining ~74 skills one by one. Each skill = one child WI = one small PR = ~30 minutes of work. Cap at 5 child PRs in flight at once to avoid review fatigue.

## Why this is a meta-WI rather than a single WI

- The work is genuinely per-skill — different skills have different phase counts (`design-tech` is large, `quick-fix` is tiny).
- Per-skill PRs let reviewers focus.
- A single mega-WI would generate a 70+ file diff that no reviewer can meaningfully audit.

## Per-child-WI scope

For each remaining skill X:

1. File `WI-CHILD-<X>` (use canonical sequential WI ID at filing time).
2. Read the skill's process; extract phases.
3. Add `phases:` block to SKILL.md frontmatter.
4. If the skill has tier-2 scenarios, add at least one `jq`-based receipt structure assertion. Skills without tier-2 scenarios are exempt from this step (Phase D will catch missing receipts globally anyway).
5. Open PR labeled `phase-c-migration`.

## Acceptance criteria for the meta-WI

- AC1: Every skill in `skills-manifest.json#includedSkills` has a `phases:` block in its SKILL.md, OR has an explicit `phases_exempt: true` flag in frontmatter with a documented reason (e.g., `quick-fix` is too short to phase).
- AC2: Tier-1 validator `validate-skill-receipt-shape.sh` reports zero unmigrated skills.
- AC3: All `phase-c-migration`-labeled PRs are closed (merged or rejected with reason).
- AC4: An exemption registry at `references/phase-receipts-exemptions.md` documents every skill that opted out and why.

## Cadence

- Soft cap: 5 child PRs in review at once.
- Soft target: 5 skills migrated per week → ~15 weeks elapsed for 74 skills.
- Hard gate: Phase D (WI-213) cannot land until Phase C completes.
