## Audit Verdict — DUPLICATE / NEEDS VERIFICATION

Audit was unable to verify the `track-visuals/SKILL.md` mode field directly. The framing also overlaps significantly with WI-162 (the three-skill-arrays consolidation question).

**Ship plan:**
1. Read `track-visuals/SKILL.md` and confirm whether `mode` is a free-text field or already machine-readable (enum).
2. If already enum-typed: close as INVALID.
3. If free-text: this is subsumed by WI-162's "schema cohesion sweep" — merge into WI-162's scope rather than fixing in isolation.

**Do not ship as standalone** — verify first, then merge with WI-162 or close.

## Problem
Both `bootstrapStartSequence` and `greenfield` lane list `track-visuals` twice — once after `design-ui` (baseline) and once after `execute-changeset` (diff). But `laneDefinitions.greenfield.skills` is a flat string array with no metadata. There's no machine-readable way to distinguish baseline from diff mode.

## Impact
The task-graph builder must infer mode from position, which is fragile. If the lane order changes, mode inference breaks silently.

## Acceptance Criteria
- [ ] Decide canonical representation (objects with `mode` field? parallel arrays?)
- [ ] Update `laneDefinitions` schema in skills-manifest.json
- [ ] Update `scripts/task-graph.mjs` to read mode metadata
- [ ] Update all lane definitions (greenfield, brownfield-feature, bugfix, refactor) consistently
- [ ] Backward compatibility: flat string arrays still parse as default mode

**Next:** `improve-framework` → `write-spec` → `plan-changeset`

## Closeout

Status: VERIFIED on 2026-05-11.

The canonical fix landed in the delivery graph compiler rather than by changing
the manifest lane arrays. `scripts/compile-delivery-graph.mjs` now emits
browser-visible `track-visuals` tasks with machine-readable
`metadata.mode: baseline` and `metadata.mode: diff`, positioned around
`execute-changeset`. `scripts/validate-delivery-graph.mjs` rejects
browser-visible graphs that include visual tasks without both modes.
