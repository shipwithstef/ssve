# WI-142: Industry Grounding becomes default — knowledge-base read at gate, never web-fetch

**Type:** framework
**Status:** VERIFIED
**Severity:** critical
**Filed:** 2026-05-02
**Source:** Promoted from `proposals/2026-05-02-competitive-grounding-as-default.md`. Delta on WI-140 — fixes the selective-blindness that survived WI-140's keyword-scoped gate.
**Lane:** framework
**Supersedes-scope-of:** WI-140 (keeps WI-140's primitive layer; widens the trigger surface)
**Companion:** WI-143 (refresh-competitors skill + 30-competitor floor — deferred until WI-142 lands)

## Symptom

WI-140 fixed the SDKG primitive layer (engine + schema + validators + hook router) and added a `## Competitive Risk Assessment` gate, but that gate only fires when a feature spec's ACs match `earn|redeem|verify|enroll|loyalty|points|reward`. Every other feature ships without competitive grounding. This recreates the exact failure mode WI-140 set out to fix — selective blindness — just narrowed to a different keyword set.

User correction: competitive grounding is the COMPASS for every feature decision, not a keyword-matched subset. You can swim beyond the industry, but you must know where the industry is before you choose to.

## Root causes

1. **Keyword trigger in `validate-feature-competitive-cross-reference.sh`** — feature only gets the gate if AC line matches core-mechanic regex. Type:Enabler / Type:Integration are blanket-exempt.
2. **Gate-time architecture is web-fetch-shaped** — even the populated branch implies fetching to verify, which would be slow + expensive per spec.
3. **`research` and `svc-advisor` only auto-surface competitive context when topic matches `competitive-domains.json`** — domain list acts as a gate, not a priority hint.
4. **Section name "Competitive Risk Assessment" frames it as risk, not grounding** — risk is one of four required answers, not the whole frame.

## Fix direction

Knowledge-first architecture: gate READS from `references/knowledge/competitors/<slug>/` (per-competitor exhaustive deep-dive files), NEVER triggers web research from gate path. Knowledge gaps queue out-of-band deep-dive WIs but do not block the spec — gate records the gap explicitly and proceeds with available data.

Five additive changes to the WI-140 baseline:

### A. Remove the keyword trigger

`tier-1 validate-feature-competitive-cross-reference.sh`: every feature spec moving to BASELINED requires `## Industry Grounding` section. Exemption only via explicit `landscape_inapplicable_reason` field in spec frontmatter (logged + reviewed). Type:Enabler / Type:Integration get the section too — "what do other framework projects do for this enabler / integration."

### B. Rename + restructure the section

`## Competitive Risk Assessment` → `## Industry Grounding`. Four required parts (none optional):

```markdown
## Industry Grounding

**Source:** references/knowledge/competitors/index.md (last_verified: <date>, N=<count>)
**Landscape state:** populated | nascent | none-found | inapplicable

### What the industry does (baseline from training + live data)
<2-3 sentences combining LLM domain knowledge with live competitor patterns>

### What we're doing
<our chosen approach, named clearly>

### Why we differ (or align)
<one of: cost / moat / capability / regulatory / first-mover-bet / personal-preference / other-justified>
<specific evidence — not "we think it's better">

### Reversibility
<two-way door (reversible) | one-way door (irreversible)>
<if one-way: explicit risk acknowledgement>
```

### C. Knowledge-base read path (gate-side)

`scripts/lib/structured-gate-engine.mjs` (from WI-140) gains a `readKnowledgeBase(competitorSlugs, topic)` function that:
- Reads `references/knowledge/competitors/<slug>/CAPABILITIES.md` + topic-specific files
- Returns structured grounding data WITHOUT web fetch
- If knowledge missing/thin: emits `knowledge-gap-detected` finding, queues deep-dive WI stub in `.svc/framework-gaps.jsonl`, gate proceeds with available data + records gap in spec's Industry Grounding section ("Note: insufficient knowledge for X; deep-dive queued as WI-XXX")

NEVER calls WebSearch / fetch from the gate path.

### D. `research` + `svc-advisor` always-surface

When `references/knowledge/competitors/index.md` exists for the project, both skills append a competitive context block to every response, regardless of whether the query topic matches `competitive-domains.json`. The domain list becomes a *priority hint* (auto-surface even when stale), not a gate.

### E. Brownfield sweep widening

`onboard-repo` Step 2.4 (added in WI-140) currently greps for core-mechanic patterns. Replace with: enumerate all major feature areas in the codebase (per directory + entry-point analysis), invoke `analyze-competitors` per area in scoped mode. Output `docs/specs/brownfield-competitive-flags.md` covers ALL detected feature areas with severity rating.

- AC-04 — Knowledge-gap path: when knowledge thin, gate emits finding + appends stub to `.svc/framework-gaps.jsonl` + records gap in spec; gate does NOT block.

- AC-09 — `references/framework-learnings.jsonl` has new entry: `competitive-grounding-must-be-default-not-keyword-gated` (confidence 9), `gate-must-read-not-fetch` (confidence 9), `knowledge-gap-records-not-blocks` (confidence 8).

## Why critical severity

WI-140 acknowledged the principle but limited it to a keyword-matched subset. That replicates the original failure mode for every non-mechanic feature. Same archetype as WI-139 / WI-141: skill self-grades PASS on incomplete coverage. The cost of leaving this is that every non-loyalty/non-rewards feature ships without grounding — same selective blindness, different keyword.

## Cost

- ~1 SKILL.md edit per affected skill (validate-feature, write-spec, design-tech, research, svc-advisor, onboard-repo)
- 2 new validators
- 1 spec template rewrite + one-time codemod for existing specs
- New `readKnowledgeBase` function in existing engine
- Estimated: 3-4 PRs, 1-2 sessions

## Out of scope (deferred to WI-143)

- New `refresh-competitors` skill + scheduled weekly routine
- Raising competitor floor from current cap to 30
- Splitting `analyze-competitors` into one-shot vs refresh modes

These are clean additions but bundling them with WI-142 violates the plan-changeset multi-axis-risk rule. Land WI-142 first, then file WI-143 with evidence the read path works.
