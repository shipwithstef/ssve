## Problem

WI-314 adds the deprecated-foundations registry, scanner, and edit-time hook,
but the proposal also calls for periodic registry refresh, first-hit
whole-codebase scans, and promotion of confirmed deprecated-foundation findings
into durable memory/learning surfaces. Those lifecycle pieces remain separate
from the first enforcement slice.

## Acceptance Criteria

- [x] Add a registry freshness policy for `references/deprecated-foundations.json`.
- [x] Run or schedule a whole-codebase scan when a deprecated foundation is
      first detected in a project.
- [x] Define where confirmed project-local deprecated foundation findings are
      promoted for future sessions.
- [x] Add tier-1 fixtures for stale registry metadata and first-hit scan
      behavior.

## Route Recommendation

Run after WI-314 proves the initial scanner and hook path.

## Implementation

- Added `freshness` metadata to `references/deprecated-foundations.json` with
  review age, owner skill, stale action, first-hit scan requirement, promotion
  ledger, and lifecycle policy pointer.
- Added `references/deprecated-foundations-lifecycle.md` to define the registry
  refresh policy, first-hit whole-codebase scan, and promotion surface.
- Added `scripts/validate-deprecated-foundations-registry.mjs` and extended
  `scripts/lib/deprecated-foundations.mjs` so stale or malformed registry
  metadata fails mechanically.
- Extended `scripts/scan-deprecated-foundations.mjs` with
  `--first-hit-codebase-scan` and `--promote-findings` so the first project hit
  scans the repo root and promotes confirmed findings to
  `.svc/deprecated-foundation-findings.jsonl`.
- Added `scripts/validate-deprecated-foundation-findings.mjs` to validate the
  promoted findings ledger.
- Updated `design-tech`, `plan-changeset`, and the inertia hook block message
  to require the freshness check, first-hit scan, and promotion ledger.
