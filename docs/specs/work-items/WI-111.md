# WI-111 — ingest-guide: deep cross-evaluation stages

## Problem

Today's `ingest-guide` skill ran on a LinkedIn Ads Kit promo post (2026-04-25) and produced
a defensible but **shallow** report. It correctly extracted 8 claims and routed them through
extract → claim-compare → experiment → benefit → route, but it skipped four cross-evaluation
checks the builder explicitly expects:

1. **Catalog cross-check** — the skill compared claims only against `references/knowledge/`
   (per current Step 2) and missed scanning `skills-manifest.json` / the actual skill set for
   functional overlap. As a result, the LinkedIn Ads Kit's 10 satellite skills (e.g.
   `buyer-quality-audit`, `pipeline-brief-writer`) were never matched against existing svc
   skills like `build-personas`, `audit-implementation`, etc.
2. **EXTERNAL_ADDONS dedup** — the skill never checked `EXTERNAL_ADDONS.md` to determine
   whether the ingested kit duplicates an already-blended source (gstack/superpowers/OMCC) or
   whether it should be added as a new external addon entry vs blended in via `blend-external`.
3. **Research-deepening** — the skill's Step 1 delegates extraction to `research`, but does not
   require fetching the **actual upstream source** when the post references a public repo
   (e.g. `TheMattBerman/linkedin-ads-kit`). The skill ingested only the marketing copy, not
   the real `SKILL.md` files in the repo.
4. **Project-fit query** — the skill produces a "product project benefit" framing (Step 4a)
   but does not call `capability-concierge` to ask the load-bearing question: **does any
   currently-shippable project benefit from this enough to warrant action this quarter?** A
   pattern that's well-extracted but has no project to land in is dead-letter knowledge.

The user articulated this gap directly:
> "I asked this skill to actually evaluate techniques check against what internal and
> external addon skill do maybe check knowledge and figure out if we can test for what and
> if there is value so yes extract but we also have research and blend the ingest should be
> able to interact with them and figure eventually is that external addon is it duplicate
> to something do we need to merge external in our own etc eventually figure out do we have
> a project that can use this and benefit etc."

## Scope

Edit `ingest-guide/SKILL.md` to add four new pipeline stages and one new decision branch.
Pure skill-contract change — no script edits, no script additions in this WI. The new stages
delegate to existing skills (`research`, `blend-external`, `capability-concierge`) so the
work is **wiring**, not **new behavior implementation**.

### In scope

- Add Step 2.5 — **Catalog cross-check** (scan `skills-manifest.json` and the actual skills
  directory for functional overlap with each claim).
- Add Step 2.6 — **EXTERNAL_ADDONS / blend dedup check** (grep `EXTERNAL_ADDONS.md` and
  `references/blend-registry.json` for the source; if the source looks like a multi-skill
  pack, route the routing decision through a new **`blend-or-link`** branch that hands off
  to `blend-external`).
- Promote Step 1 — explicitly REQUIRE `research` to attempt fetching upstream sources (GitHub
  repos, gist URLs, primary docs) when the pasted content cites them, before classifying.
- Add Step 4.5 — **Project-fit query** (invoke `capability-concierge` for the active project
  list and tag each surviving claim with `applicable_projects: [<id>...]` or `none`; if `none`
  the claim's default routing tilts toward `discard` or `store-as-reference`, never `promote`).
- Update Step 6 — add a fourth routing option **`blend-or-link`** (in addition to discard /
  store / promote) routing to `blend-external` when overlap detected with addon ecosystem.
- Update self-verify table — add 4 new checks aligned to the new stages.
- Update chain section — note new downstream skills (`blend-external`, `capability-concierge`).
- Update output report template under `docs/specs/ingest-guide/<source-id>.md` to include the
  new sections (catalog-overlap, addon-dedup, project-fit).

### Out of scope

- New scripts (e.g. an automated catalog-scan script) — defer to a follow-up WI if usage shows
  it's needed. v1 uses grep + Read calls.
- Modifying `research` or `blend-external` SKILL.md.
- Re-running every prior ingest — only the LinkedIn Ads Kit post will be re-validated.

## Acceptance criteria

1. `ingest-guide/SKILL.md` contains documented stages for catalog cross-check, addon-dedup,
   research-fetch-required, and project-fit query.
2. The pipeline section shows the new flow `extract → catalog-cross-check → addon-dedup →
   classify → experiment → benefit → project-fit → rubric → route` with the four routing
   options (discard / store / promote / blend-or-link).
3. The self-verify table contains ≥10 checks (was 10, now ≥14) with one check per new stage.
4. `node scripts/lint-skills-manifest.mjs` exits 0.
5. Tier-1 evals pass (skill-structure, contracts, chain-references, self-verify-sections,
   worktree-safety).
6. A re-ingest of the LinkedIn Ads Kit post under the new skill produces a report that
   mentions: at least one catalog overlap, an addon-dedup verdict, a `research`-fetched
   upstream excerpt OR a justified skip, and a project-fit verdict referencing
   `capability-concierge`.

## Risk

LOW — skill-contract change, no scripts touched, falls back to existing skills already in
the framework. Failure mode: the new stages might prove too heavy for short ingests. Mitigation:
each new stage has an explicit short-circuit ("if N/A, log skip and proceed").
