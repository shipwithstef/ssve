## Problem

Base44 and similar low-code backends need framework-native verification for persistence, RLS/security exploitability, caller-surface deployment order, and derived ownership patterns. Several proposals describe the same root class: agents should not infer backend correctness from UI symptoms or schema intent when the actual data path can be probed.

## Acceptance Criteria

- [x] Add a persistence-bisect phase to diagnose-bug for "expected visible, got empty/zero" symptoms.
- [x] Add an `audit-entity-rls` flow or equivalent mode for Base44 user-app entities.
- [x] Require exploitability probes before deploying security/RLS rules, then re-probe after the fix.
- [x] Define RLS deployment order by caller surface and blast radius, not alphabetical order.
- [x] Document and validate derived ownership patterns: denormalized owner, defense-in-depth secureOperation, or function gateway.
- [x] Add replay fixtures for empty-list persistence failures and RLS false-confidence failures.

## Route Recommendation

Run through `improve-framework`; likely touches `diagnose-bug`, `base44-environment`, `review-security`, and validators.

## Notes

This is intentionally grouped as one Base44 verification pack to avoid five separate proposal-only security/data rules with overlapping probes.
