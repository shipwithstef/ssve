# WI-301: Delivery graph closeout classification and retrospective closure guard

## Goal

Merge the completion-scope parity and retrospective closure proposals into the delivery graph model so closeouts cannot confuse runtime proof with framework completion.

## Closeout States

Allowed states:

- `runtime-accepted`: runtime/prod behavior passes, but one or more framework evidence families are missing.
- `corrective-closure-complete`: a retroactive/corrective pass repaired evidence, but the original execution was incomplete.
- `framework-complete`: compiled graph is satisfied, mandatory skills ran or have valid N/A evidence, and promotion evidence exists where required.
- `blocked`: required evidence cannot be obtained or a mandatory skill failed.

## Acceptance Criteria

- AC1: `route-workflow` and `verify-promotion` require one closeout classification for mutating, deploy-affecting, end-to-end, corrective, and framework-evolution runs.
- AC2: `framework-complete` is forbidden unless every required evidence family is `satisfied` or validly `n/a`.
- AC3: Corrective/retroactive closures require route-workflow phase receipts, route decision-log evidence, upstream skip ledger, audit-implementation mode selection when relevant, and post-merge verification status.
- AC4: A closeout with production probes but missing lane graph, E2E/review/PR evidence, or skip ledger is classified `runtime-accepted`, not `framework-complete`.
- AC5: Replay fixtures cover the Example Marketplace WI-233 closeout class described in the source proposals.
