# WI-492: Authenticated owner capability for task-state migration

**Type:** framework security hardening
**Status:** identified
**Severity:** medium
**Filed:** 2026-07-17
**Source:** WI-486 exec review round-3 finding R3-004 (dispositioned accept-with-justification at the 3-round cap)
**Lane:** framework
**Related:** WI-486

---

## Problem

`scripts/svc-migrate-task-state.mjs` (the only on-disk task-state rewrite path,
WI-486 SIB-30) gates migration on a **structured but self-asserted JSON
authorization** — it names the repository, exact WI, an authority principal,
issuance/expiry, and a nonce, and is verified for shape/scope/freshness before
the migration lock is taken. That is an attributable, scoped, expiring floor,
but the authorization file is still **agent-writable**: an agent with write
access to the repo could mint its own authorization. It is not a
cryptographically authenticated owner capability issued through a channel
outside agent-writable scope.

This was accepted as a logged residual risk at the WI-486 review cap because the
migration CLI is an explicit **operator/setup tool**, never invoked in the normal
agent mutation path, and the structured-auth floor is sufficient for that use.

## Proposed fix (scope)

Introduce an authenticated owner capability for `svc-migrate-task-state.mjs`:
- A capability issued through an owner-controlled channel outside agent-writable
  scope (e.g. an owner-signed token, an OS-keychain / env-injected secret, or a
  detached signature verified against a trusted public key committed by the owner).
- Bind the capability to repository identity + WI + exact operation + graph digest
  + session, single-use (nonce ledger), with expiry.
- Verify the capability's authenticity (not just its shape) before the migration
  lock is taken; record the verified principal + capability id in the receipt.

## Acceptance criteria

- [ ] MIG-CAP-01: migration/restore refuses an authorization that is not authenticated against an owner-controlled trust anchor (an agent-minted JSON no longer authorizes).
- [ ] MIG-CAP-02: the capability is bound to repo + WI + operation + graph digest and is single-use (replay rejected via a nonce ledger) and expiring.
- [ ] MIG-CAP-03: the receipt records the verified principal + capability id; a forged/expired/replayed capability produces a terminal `rejected` receipt with no bytes changed.
- [ ] MIG-CAP-04: tier-1 fixtures prove authenticated-accept, forged-reject, expired-reject, replay-reject — hermetic, no network.

## Notes

Deferred from WI-486 (atomic-bootstrap + bounded-migration scope). The WI-486
floor — structured, attributable, repo+WI-scoped, expiring authorization under a
per-graph migration lock with immutable content-addressed backups and terminal
receipts — remains in place and is not regressed by this WI.
