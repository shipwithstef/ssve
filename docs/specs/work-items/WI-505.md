## Problem

`svc-ensure-worktree` rejects an existing stale foreign complete v1 binding/claim tuple before reaching its already generation-bound claim transfer. `activeBindingOwner()` treats the first unreleased binding JSON as live authority without correlating claim security, ownership, freshness, path, or generation. Users are therefore forced toward manual deletion, old-session impersonation, or break-glass even though the documented automatic recovery transition is safe and eligible.

WI-505 restores that transition without weakening fail-closed behavior, deleting the worktree, or changing WI-502's v2 authority and explicit migration contract.

## Root cause

**Immediate:** `resumeExisting()` checks coarse unreleased-binding ownership before it checks claim freshness and invokes `transferClaim()`.

**Enabling:** resume and transfer do not share a secure exact tuple classifier, and transfer changes the claim without retiring the exact source binding.

**Systemic:** bindings were used as independent liveness evidence while tests covered complete bootstrap and claim CAS separately rather than the public joined transition.

## Selected diagnosis

Use one shared secure v1 tuple classifier for resume and locked transfer. The transfer validates the exact stale source tuple and expected generation, checks active v2 precedence before mutation, writes generation+1 as the authority linearization point, and retires the exact old binding. A claim-aware `activeBindingOwner()` or binding retirement alone is insufficient.

Technical design must finalize lock ordering, crash recovery, v2 query timing, ambiguity rules, and the precise loser diagnostic before code changes.
