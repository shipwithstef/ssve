# WI-498: install-anchored script/hook/enforcer resolution (security) + Codex first-task activation

**Type:** bugfix + security (untrusted-path / consumer-shadow exec class)
**Status:** identified
**Severity:** high — (a) Codex sessions in onboarded repos deadlock at bootstrap; (b) svc resolves executable script paths from the **consumer repo's working tree/cwd**, an arbitrary-code-execution vector (a consumer-planted `scripts/task-graph.mjs` would be executed).
**Filed:** 2026-07-18
**Source:** owner — "we initiate scripts/hooks in the framework repo, but consumer product repos are missing the scripts and can't run from the svc location. The right thing is to resolve from the single svc install and execute from there, not vendor into each product." Confirmed by research (pre-commit central-store, `import.meta.url` self-location; git `core.hooksPath`-override RCE class) and by svc's own dominant convention.
**Lane:** framework
**Related:** WI-494/496 (bootstrap/loader install-binding — same family), WI-486 (loader receipt). Subsumes plan-review findings F-003, F-011, F-013.

## The principle

> **Every svc executable path — in scripts, in hooks, and in what the Codex enforcer authorizes — MUST be anchored to the svc install (self-located via `import.meta.url`/`__dirname`, tamper-resistant through the consumer symlink), NEVER derived from the consumer repo's `cwd`, `worktree`, walked-up tree, or `.git` config.**

Deriving an exec path from consumer-controlled state is the same RCE class as git `core.hooksPath` overrides. `import.meta.url` resolves to the REAL install even when invoked through the `~/.claude/skills` / codex-farm symlink (node default, verified), so install-anchoring is both correct for missing-consumer-code AND tamper-resistant. svc already does this in ~20 scripts (`scenario-runner.mjs`, `init-project-state.mjs`, and `svc-phase-receipt-autoemit.mjs` even computes `SVC_ROOT` but bypasses it at the exec site). This WI finishes the convention and guards it.

## Problem — two coupled defects

**D1 — consumer-relative exec-path resolution (security + deadlock root cause).** Sites resolving an svc executable from the consumer base:
- `scripts/codex-load-skill.mjs:40` → `path.join(worktree, "scripts", "task-graph.mjs")` then `spawnSync` — onboarded repos lack it ⇒ loader fails; a planted copy ⇒ ACE. (plan-review F-003)
- `hooks/svc-phase-receipt-autoemit.mjs:113` → `path.join(cwd, …)` despite `SVC_ROOT` already computed at line 13.
- `hooks/svc-lane-tasks-validate-{edit,content}.mjs` → walk UP the consumer tree to find+exec `task-graph.mjs`.
- `scripts/validate-wave-closeout.mjs:268` → `path.join(root, "scripts", "task-graph.mjs")`.
- `hooks/opencode/svc-opencode-plugin.ts:165` → consumer `scriptsPath`.

**D2 — the enforcer authorizes a consumer-relative loader token (plan-review F-011, CRITICAL).** `active.ok===false` authorizes `node scripts/codex-load-skill.mjs …` (relative), which node resolves against cwd — a shadowed copy in a nested cwd = ACE. Same class as the WI-494 bootstrap-shadow bug, unfixed for the loader token.

**D3 — the Codex first-task activation deadlock (the user-facing symptom).** Bootstrap creates task 1 `pending`; the enforcer needs an `in_progress` task for any governed mutation; the loader records a receipt but never activates the task; `set-status` is itself denied ⇒ no path pending→in_progress. Codex-only (Claude has no enforcer). Fixing D1 (loader runs the install's `task-graph.mjs`) is the prerequisite for a clean activation.

## Fix

1. **Install-anchor every D1 exec-path** to the self-located install root (`path.resolve(path.dirname(fileURLToPath(import.meta.url)), "..")`, realpath-canonicalized), keeping `cwd: worktree` only for the child's working directory. Honor an `SVC_HOME`-style env override ONLY when it points at a validated install marker (`skills-manifest.json`), else fall back to self-location.
2. **D2/F-011:** the enforcer authorizes the loader token ONLY as the install-absolute path realpath-equal to `installedLoadSkill()`; the relative form is refused (or requires `realpath(cwd)===repo_root`, mirroring the WI-494 bootstrap fix).
3. **D3:** new atomic `task-graph.mjs activate-skill` command (Codex-only caller) — one `updateJsonAtomic` read-validate-write that verifies the target is the exact first-runnable-pending (via `recoverableId`, string+number domain) or the exact already-in_progress reload, then writes `skill_receipt`+`status:in_progress` together. `codex-load-skill.mjs` calls it via the install-anchored, canonically-bound sibling; session receipt written only on exit 0.
4. **Anti-regression:** a tier-1 guard that FAILS on any new consumer-relative (`cwd`/`worktree`/walk-up) resolution of an svc executable path.

## Acceptance criteria

- [ ] IAR-01: every D1 site resolves its svc executable from the install root (self-located), proven by reading each fixed site; `cwd:worktree` retained only as the child workdir.
- [ ] IAR-02 (**security**): in an onboarded fixture repo containing a PLANTED `scripts/task-graph.mjs`, the fixed loader/hooks execute the **install** copy, never the planted one — proven by a fixture asserting the install copy ran.
- [ ] IAR-03 (**F-011**): the enforcer authorizes the loader token only as the install-absolute path; a relative or shadowed token is DENIED — hermetic fixture.
- [ ] IAR-04 (**deadlock, hermetic**): bootstrap (task pending) → loader ALLOW → execute installed loader → task `in_progress` + both receipts → governed mutation ALLOW — driven against the REAL enforcer in an isolated fixture (not just live). Covers numeric + string task ids.
- [ ] IAR-05: atomic `activate-skill` — single `updateJsonAtomic`; non-first/completed target fails closed leaving graph + session receipt byte-identical; idempotent in_progress reload performs no graph write; failure-injection proves exact-loader retry restores an authorized state.
- [ ] IAR-06: no new enforcer exemption for `active.ok===false` beyond loader+bootstrap; Claude host (`skill_tool`) path unchanged (`load-skill`/`set-status` byte-identical; `activate-skill` additive, Codex-only caller).
- [ ] IAR-07: anti-regression tier-1 guard fails the build on any new consumer-relative svc-exec-path resolution.
- [ ] IAR-08: tier-1 green (`run-all-evals.sh --tier1`) incl. the new fixtures; live re-proof in example-marketplace WI-SOCIAL-01 (loader→activation→governed-mutation ALLOW).

## Documented follow-up (candidate WI-499): enforcer↔operation task-id domain unification

G6 review (F001) flagged that the enforcer/shape authority layer accepts the `recoverableId` **string+number** domain (WI-486 EXEC-R3-001; migration/binding/authority tier-1 fixtures legitimately exercise string-id graph SHAPES), while task-graph OPERATIONS (`validateTask`, `set-status`, `load-skill`, and this WI's `activate-skill`) are numeric-only. A hypothetical string-id graph would be authorized by the enforcer but rejected by `activate-skill`.

**Why not fixed here — and why WI-498 does not worsen it (G6 R3-F001):** non-numeric task-id graphs DO exist in production (e.g. planner/onboard graphs with `["validate","impl",…]` ids). But the task-graph OPERATION layer was ALREADY numeric-only before this WI: the loader that `codex-load-skill` invoked previously (`task-graph load-skill`, `Number()`-based) equally rejects string-ids, as do `set-status`/`record-phase`. `activate-skill` inherits exactly that pre-existing numeric limitation — it does not introduce or widen a deadlock; a non-numeric graph is rejected with the SAME clear error the prior loader produced (fixture asserts: rejected + byte-identical, NO fail-open, NO silent hang). The genuine inconsistency is pre-existing and framework-wide: the enforcer/shape AUTHORITY layer accepts the `recoverableId` string+number domain (WI-486; 4 migration/authority tier-1 fixtures depend on it) while EVERY task-graph operation is numeric-only. Tightening the shape validator to numeric breaks those 4 fixtures. Unifying the id-domain across the enforcer, all task-graph operations, and those fixtures is a bounded, framework-wide change tracked as **WI-499** — out of scope for WI-498, which neither creates nor worsens the gap.
