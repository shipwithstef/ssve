## Goal

Store and check receipts by `{receipt_type, wi, target_sha, phase?}` so two WIs
on one SHA cannot destroy each other, and refuse Stop success, VERIFIED status,
or final “done” when canonical receipts fail.

## Boundaries

In scope: `emit-receipt.mjs` note envelope keying, `check-chain-receipts.mjs`,
Stop/task-completion guards, verify-promotion status writer.

Out of scope: bulky review *bytes* (WI-547 store), host adapter chmod (WI-545),
shared policy (WI-549), dispatch (WI-551).

Do not rewrite historical receipt bytes. Legacy single-key notes remain readable;
new writes use composite keys. A relocation/index overlay may map the old
single-key slot to the WI that originally owned it when provenance is unique.

## Acceptance Criteria

- [ ] AC-550-1: Emitting `verify-promotion` for WI-542 then WI-543 on the same SHA preserves both notes.
- [ ] AC-550-2: A second write of the same `{type, wi, sha, phase}` is rejected unless an explicit supersession contract is present and hashed.
- [ ] AC-550-3: `check-chain-receipts --sha <sha> --wi WI-542` does not pass using WI-543’s receipt.
- [ ] AC-550-4: Stop / task-completion / VERIFIED / final success re-run canonical receipt validation against the exact closeout SHA and fail closed on missing/invalid envelopes.
- [ ] AC-550-5: Task-graph `completed` is an index. It cannot override a failed canonical check.
- [ ] AC-550-6: Focused tests cover dual-WI same-SHA, overwrite refusal, Stop denial, and a valid dual-WI completion path.
- [ ] AC-550-7: No paid provider is invoked. Stage receipts from WI-521 remain a separate hash-linked object.
- [ ] AC-550-8: Two concurrent writers emitting distinct `{type, wi}` keys on one SHA both survive, or one fails closed without deleting the other. The primitive is lock/CAS/retry, not check-then-write.
- [ ] AC-550-9: Each completion consumer validates the SHA and receipt identities in the transition matrix below.

## Migration

Read old notes as `{type → receipt}`. When a historical slot has a `wi` field,
project it into `{type, wi}`. When it does not, treat it as the unique owner of
that type@sha if only one WI is claimed; otherwise fail closed and require an
explicit owner map (no guessing).

## Transition matrix

| Consumer | Canonical SHA | Required identities | Fail closed |
|---|---|---|---|
| execute-changeset complete | current tree / staging SHA | `plan-manifest`, `review-plan`, `exec-record` for that WI | missing/invalid envelope |
| review-exec / audit | implementation candidate SHA | `exec-record`, `review-exec` or `audit-implementation` for that WI | missing/invalid |
| Stop / task-completion | HEAD of the bound worktree | required envelope for the active WI at that SHA | deny success |
| verify-promotion / VERIFIED | promoted / closeout SHA | `verify-promotion` for that WI | no VERIFIED write |
| final report | same SHA the report names | checker `ok:true` for that SHA+WI | no “done” |

## Rollback

Disable new composite writes. Keep composite reads plus the legacy projection.
Do not restore type-only last-wins writes as the live path.
