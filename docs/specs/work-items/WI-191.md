# WI-191: Phase contracts + execution-trace receipts for every skill (host-agnostic)

## Why this is the highest-leverage fix in the 2026-05-09 review

A skill today can emit the right output artifact and the framework just trusts that the discovery, verification, and audit phases ran. There is no machine-readable contract for what the skill PROMISED to do, and no receipt for what it ACTUALLY did. This single missing primitive subsumes:

- **F-027** (user-delegated verification) — receipts must carry `evidence_level`
- **F-029** (V0 bundle-grep substitution) — receipts must carry V1+ artifacts on browser-visible tasks
- **F-020** (write-journeys process gaps) — receipts prove discovery + AC mapping ran
- **F-023** (tier-2 string-existence assertions) — receipts replace presence checks with structured fields

WI-191 is the meta-primitive WI-197 and WI-199 ride on top of. They build the V-ladder slice of the receipt schema; WI-191 generalizes that to "every declared phase produces a verifiable receipt entry."

## The host-agnostic constraint (lesson from supersession)

The 2026-04-23 proposal failed because its enforcement layer was a Kimi-only Flow Skill. Phase-receipt enforcement MUST work on every host the framework provisions. The only mechanism that satisfies that constraint today is:

- A Stop hook that reads `.svc/lane-tasks-<WI>.json` after task completion
- A schema-validating reader against the active task's declared phases
- Tier-1 validators that inspect the receipt at rest

This is the same Stop-hook surface WI-197 (verification-delegation) and WI-199 (V0 substitution) already use. Reuse, don't duplicate.

## The actual gap (precise)

1. **No phase declaration in skill frontmatter.** Skills describe processes in prose ("Step 1: Reproduce", "Step 2: Root cause"). Grep across all `*/SKILL.md` for `## Execution Phases`, `## Phases`, `phase.contract`, `execution trace` returns zero matches. There is no machine-readable contract for what a run must touch.
2. **No receipt in lane-tasks.** `.svc/lane-tasks-<WI>.json` records `status: completed` but not `phases_executed[]`. A run that skipped half the phases looks identical to a run that hit them all.
3. **No tier-1 validator on receipts.** Even where a skill declares phases informally in its body, no validator asserts the corresponding receipt entries exist.
4. **No tier-2 trace assertions.** Tier-2 scenarios assert output presence (`grep "root cause"`) instead of process execution (`receipt.phases_executed[].id == "P3-RootCause"`).

## Proposed Fix — three layers

### Layer 1 — Schema (non-blocking opt-in)

Add a `phases:` block to skill frontmatter. Each phase declares: `id`, `trigger` (`always` / `mode:<X>` / `flag:<Y>` / `after:<phase>`), `reads[]`, `writes[]`, `evidence_kind` (`file` / `command_output` / `screenshot` / `live_dom` / `none`), `required_for_completion` (boolean).

```yaml
phases:
  - id: P0-PreFlight
    trigger: always
    reads: [".svc/lane-tasks-<WI>.json", "FRAMEWORK-STATE.md"]
    writes: []
    evidence_kind: command_output
    required_for_completion: true
  - id: P3-RootCause
    trigger: mode:diagnose
    reads: ["code", "logs", "spec"]
    writes: ["docs/specs/work-items/WI-<n>-root-cause.md"]
    evidence_kind: file
    required_for_completion: true
```

### Layer 2 — Receipt (the new contract entry)

Extend `.svc/lane-tasks-<WI>.json` task entries with a `skill_receipt.phases_executed[]` array:

```json
{
  "task_id": "T1",
  "status": "completed",
  "skill_receipt": {
    "skill": "diagnose-bug",
    "phases_executed": [
      {"id": "P0-PreFlight", "ts": "...", "evidence_artifacts": [{"type": "command_output", "path": "..."}]},
      {"id": "P3-RootCause", "ts": "...", "evidence_artifacts": [{"type": "file", "path": "docs/specs/work-items/WI-187-root-cause.md"}]}
    ],
    "evidence_level": "V2",
    "target_class": "browser-visible"
  }
}
```

The `evidence_level` and `target_class` fields are the same ones WI-197 and WI-199 introduce — single shared schema.

### Layer 3 — Enforcement (the host-agnostic gate)

Three primitives, all of which already exist as patterns elsewhere in the framework:

1. **Tier-1 validator `validate-skill-receipt-shape.sh`.** For every task in every active and recently-completed `.svc/lane-tasks-*.json`, fail if a phase declared `required_for_completion: true` is absent from `receipt.phases_executed[]`.
2. **Stop hook extension to `svc-task-completion-guard.sh`.** Before allowing a task to transition to `completed`, parse the skill's phase block and the task's receipt. Block on missing required-phase entries with an actionable diff. Reuses the same hook surface WI-197/WI-199 wire into.
3. **Tier-2 trace assertions in scenario fixtures.** Convert string-existence checks (`grep "root cause"`) to receipt structure checks (`jq '.skill_receipt.phases_executed[] | select(.id == "P3-RootCause")'`).

## Migration strategy (avoids ceremony fatigue)

Big-bang adoption across 79 skills will fail. Phased rollout:

- **Phase A (1-2 days):** Land the schema + receipt + tier-1 validator + Stop hook with `required_for_completion` defaulting to `false` (advisory mode). Existing skills emit no `phases:` block; validator reports skills with zero declared phases as ADVISORY findings, not failures. No skill is forced to migrate yet.
- **Phase B (rolling):** Pick the canonical 5 skills first — `diagnose-bug`, `test-journeys`, `write-journeys`, `verify-promotion`, `execute-changeset`. Author their `phases:` block. Receipt enforcement flips to blocking only for these 5. Tier-2 scenarios for these 5 gain trace assertions.
- **Phase C (per-skill backlog):** Open a child WI per remaining skill that adds its phase block + tier-2 trace assertions. Each child WI is a 30-minute change.
- **Phase D (gate flip):** Once all skills declare `phases:`, the tier-1 validator's "zero declared phases" finding flips from ADVISORY to FAIL. Stop hook enforces for every skill.

This mirrors the F-009 (preflight 0/79) and F-010 (Before Starting 5/79) migration shape — the framework already knows how to roll out per-skill gates.

- AC2: `.svc/lane-tasks-<WI>.json` task entries accept a `skill_receipt.phases_executed[]` field. Schema documented in `references/task-graph-protocol.md`.

- AC4: Stop hook `svc-task-completion-guard.sh` blocks `completed` transitions on missing required-phase entries. Shares the same wiring fix as WI-197 + WI-199 (per F-011 stdin wiring fix).
- AC5: At least 5 canonical skills (`diagnose-bug`, `test-journeys`, `write-journeys`, `verify-promotion`, `execute-changeset`) ship with `phases:` blocks and matching tier-2 trace assertions.
- AC6: Tier-2 scenarios for those 5 skills assert `receipt.phases_executed[]` shape, not string existence. Replay fixture proves a phase-skipping run now fails.
- AC7: Migration backlog WIs are filed (one per non-canonical skill) so Phase D's gate flip is mechanically tracked.
- AC8: `FRAMEWORK-STATE.md` Known Gaps entry for "Skill phase contracts and execution trace validation" closes with citation to the merged PR and the migration backlog WI list.
