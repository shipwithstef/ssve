## Problem and provenance

The September 18 Antigravity conceptual proposal, preserved as `original-proposal.md` with private examples removed, describes three modes. The shipped `scripts/sync-github-issues.mjs` only pushes local WIs outward, derives its target from the installed script, truncates issue bodies, swallows failures, and closes PROMOTED work before G7. This plan makes both concerns explicit, with separate implementation and review checkpoints.

## Mode and command contract

| Operation | local-only (default) | github-backed | hybrid-governed |
|---|---|---|---|
| Configure mode/repository | local config, no API | exact owner/repo required | exact owner/repo required |
| Local capture, onboard, list, execution | allowed offline, shows local WIs | allowed offline, including unpublished local WIs | allowed offline, including unpublished local WIs |
| `--pull N` | refuse with opt-in guidance and zero API calls | adopt selected issue as WI-GH-N | same |
| `--publish --wi WI-GH-N` | refuse with zero API calls | allowed with curated public title/body | allowed with curated public title/body |
| `--publish --wi WI-NNN` | refuse with zero API calls | refuse: switch to hybrid mode | allowed with curated public title/body |
| `--close-wi ID --commit SHA` | refuse with zero API calls | allowed after G7 note proof | same |
| `--list` and `--dry-run` | local only, zero API calls | list map/local mirrors; dry-run may read remote but never write | same |

All three mode names are accepted exact CLI/config values; local/github/hybrid are explanatory UI labels, not additional aliases. Both remote modes share the same safe remote primitives. Their observable distinction is the origin allowed for outbound publication. GitHub Issue title/body are intake material until adoption; the local mirror then owns execution/verification state. Remote edits after adoption cause a conflict on explicit re-pull or publish, never automatic reverse overwrite. Mode changes keep existing local WIs and mappings; they affect future actions only.

Config lives in worktree `.svc/config.json` under `issue_tracker` with `mode`, exact `repository` for remote modes, and `close_trigger` = `manual` (default) or `verify-promotion`. Configure is network-free, preserves unrelated keys, validates unknown/malformed settings before network, and never migrates backlog or publishes. Repo config rejects `private_terms` and secrets. Optional `~/.svc/issue-tracker-private-terms.json` is an owner-only 0600 JSON map keyed by exact repository; absence means no configured private terms. Curated public text remains the primary privacy boundary. The deterministic sanitizer removes absolute home/workspace paths and configured terms and rejects recognizable credentials, private keys, and authorization headers before any inbound tracked mirror or outbound API write; it does not claim universal secret detection.

The existing script becomes the single CLI: `--configure MODE --repo OWNER/NAME`, `--pull N`, `--publish --wi WI-ID --public-title TEXT --public-body FILE`, `--close-wi WI-ID --commit SHA`, `--adopt-issue N --wi WI-ID`, `--recover-lock`, `--list`, `--dry-run`, `--root DIR`. Legacy `--wi`, `--active`, and `--all` alone exit nonzero with explicit migration guidance and zero GitHub calls. Explicit `--root` or invocation cwd resolves a canonical Git worktree; installed script location never chooses the target. All remote paths use literal `repos/OWNER/NAME` plus `--hostname github.com`; child `gh` environment clears GH_HOST, GH_REPO, and GH_ENTERPRISE_TOKEN. No shell interpolation or raw request/secret echo. `gh` child timeout is 30 seconds within a bounded whole operation. The command refuses symlink or escaping local write targets. No installer action calls GitHub.

## Identity, pull, publish, and close interface

The shared map is `<git-common-dir>/svc-issue-tracker/map.json`, schema_version 2, keyed by configured repository and WI, with number, URL, title, state, exact marker, last_sync_sha256, owned_inner_sha256 (null before first owned block), updated_at, and optional source/mirror digests. Mutations in sibling worktrees acquire `<git-common-dir>/svc-issue-tracker/lock` with a bounded acquire wait of 215 seconds; lock records pid/host/time. This covers a recovery scan reaching 120 seconds before its last 30-second request, then one 30-second GET and one 30-second PATCH, plus 5 seconds of grace. The waiter never steals a live holder’s lock. A live foreign holder causes a bounded fail-closed error. `--recover-lock` verifies the recorded host is local and pid is dead before removing the lock; live, foreign-host, unreadable, or uncertain holders remain fail-closed. Config and WI mirrors live in the invocation worktree; map lives in the Git common dir. Writes are atomic. Changing configured repository refuses reuse of a mirror whose provenance or map names another repository. A legacy `.svc/github-issues-map.json` is validated for repository/number/URL and migrated into shared state without deleting the original. No map is treated as proof of a remote close.

Owned issue body content is delimited by exact `<!-- ssve-issue-tracker:OWNER/REPO:WI-ID:begin -->` and matching `:end -->`; `last_sync_sha256` hashes JSON.stringify([repository, wi, title, ownedInnerMarkdown]) as UTF-8 SHA256. Human text outside the block, comments, and unrelated labels remain untouched. The implementation owns no GitHub labels in v1, so no label deletion is authorized. A pulled community issue has map fields `{number,url,title:remoteTitle,marker:null,last_sync_sha256:SHA256(JSON.stringify([repository,wi,remoteTitle,""])),source_sha256}`; the empty last element is the empty owned inner markdown. Legacy markerless adoption requires existing map number, matching repository/URL, issue response without `pull_request`, and stored or supplied exact public title; otherwise conflict. A first new publish with no map creates directly without repository-wide scanning. Marker recovery runs only for a pending identity or legacy entry: list at most 10 pages of 100 issues with state=all, skipping `pull_request` items and checking exact markers. Incomplete or duplicate results refuse implicit creation. `--adopt-issue N --wi ID` resolves a pending large-repo ambiguity only after issue N has the exact managed marker and configured repository identity; title-only matches are insufficient. Before POST, persist pending identity; a lost POST response is recover-only on the next explicit run. Never blindly issue a second POST. On successful create, persist the mapping before any follow-up request. Same-state repeat is a remote no-op.

Pull accepts one selected issue, rejects PR-shaped responses, validates configured repo and URL, and writes `docs/specs/work-items/WI-GH-N.md` with heading `# WI-GH-N: title`, trusted Type/Status/Severity/Filed/Source/GitHub Issue metadata, a raw-source provenance digest, then a separated `## Imported Issue (untrusted)` body. The title is one line with controls removed and heading markers escaped. The body uses a backtick fence longer than the longest run in remote content and prefixes every imported body line with `> ` inside the fence, so bold metadata cannot match the real parser anchored at line start. Run `list_work_items.mjs --json` with hostile `**Priority:**`, `**Depends on:**`, `**Blocked by:**`, `**Dependencies:**`, `**Closed:**`, `**Filed:**`, and `**Status:**` lines; trusted severity/priority, empty dependencies, null close date and open status remain unchanged. Do not add padding or change the parser merely to pass fixtures. If remote content contains recognizable credentials or prohibited private terms, write nothing. Identical re-pull is a no-op; changed remote or local mirror is an explicit conflict. The adopted WI participates in normal routing, worktree bindings, receipts, and commit trailers. Core work stays offline after adoption.

Publish requires a reviewed public title/body for either remote mode, never uploads raw WI content, keeps the full accepted body or rejects the API size limit, and leaves the issue open even when local work is PROMOTED or VERIFIED. A pulled but unpublished mirror records an empty owned-block baseline. First publish may add the block; it changes title only when `--public-title` differs from current remote title and the recorded title hash still matches. Later publish compares owned block and intentional title updates to the last synchronized baseline; adopted issues also retain the complete source baseline so outside-block human edits remain conflicts. Before a PATCH, persist the requested title/body/inner hashes and pre-write source hash. An explicit retry reconciles an exact applied request without another write, retries an unchanged pre-write state, or retains a conflicting pending request. Publish and close cannot cross an unresolved pending operation. A maintainer title-only edit after pull does not prevent close: close checks the expected marker, owned inner content, and adopted body using the stored title. It never overwrites a current title or absorbs that title change into the source baseline; a later pull still reports it. Preview shows the exact sanitized payload but writes nothing. CLI tests must confirm no implicit bulk writes, no truncated benign >4000-byte body, and no write after a secret finding.

`--close-wi ID --commit SHA` accepts a 40-hex commit and reads authority only from the actual durable `refs/notes/svc-receipts` slot at that commit; no separately supplied receipt file or self-authored PASS object is accepted. The note must contain the same WI verify-promotion receipt. Validate that receipt through the existing receipt validator: type, WI, PASS verdict, P1–P4 PASS, P3 outcome PASS, and target_sha/tree_hash when present must match the real commit/tree. The commit must exist and be ancestor of the locally present origin default branch; query the configured repository default branch and live branch head, require the corresponding local origin ref to match that exact SHA, then check ancestry (never assume main or implicitly fetch; stale or wrong-repository evidence gives fetch/check-repository guidance). Close sends only generated, sanitized commit URL and receipt facts. If the issue has no owned block, append one at the end of the existing body, preserving all human text byte-for-byte; never send a title field on close, even if a maintainer changed it after pull. Use one PATCH for body, `state=closed`, `state_reason=completed`. Persist pending body/inner digests and commit before PATCH; clear pending only when its response confirms closed state and the exact requested body. A partial response remains pending; an explicit retry may close an already-applied desired block. Reject PROMOTED, DEPLOYED-UNVERIFIED, stale/wrong-WI/failed/unreachable evidence. `land-changeset` uses Related to rather than GitHub auto-close keywords. Manual trigger prints exact retry command with `--commit SHA` after G7. `verify-promotion` trigger passes its BASE_SHA and attempts close only after local receipt emission; GitHub failure leaves local VERIFIED and receipt unchanged and records `close-pending` in shared map, visible through `--list`.

## External state, risk, and rollback

Local consumer config and mirrors are atomic worktree files; the shared map/lock are in Git common state. GitHub owns public issues and comments; this plan only edits the owned body block, public title, and close state after explicit actions. Host installation distributes reviewed capabilities through existing setup. Databases, deployments, registries, DNS, payments, queues, analytics, and browser/device state are untouched. A local map is not evidence of remote issue state.

Rollback reverts code and tracked config changes through Git while preserving both local WI history and public issues. There is no automatic remote delete, comment rewrite, or backlog destruction. Recovery from network uncertainty requires explicit marker reconciliation; remote conflict is reported for human resolution. Regex sanitization is limited; curated public text and fail-closed credential checks are the primary privacy controls. A remote outage must not revise local verification.
