# Rule: Distribution-First Does Not Override Launch-Blockers

The "build-no-launch" / "distribution-first" framework principle (gate net-new feature work behind first-paying-customer milestone) MUST NOT be applied to UX-quality fixes on already-shipped surfaces. Agents who conflate the two redirect users to distribution work while their existing app remains hostile to those very users — making any distribution effort wasted spend.

## The three classes — gate behavior

| Class | Examples | Gate behavior |
|---|---|---|
| 🟥 **New feature** | "Add a referral leaderboard", "Build push notifications", "Add AI deal generator", "Implement loyalty challenges" | **GATED.** Apply distribution-first. Redirect to customer acquisition. |
| 🟨 **Feature polish without launch-blocking severity** | "Tune the animation timing", "Add a 7th color theme", "Improve admin dashboard charts", "Refactor for cleaner abstractions" | **GATED.** Apply distribution-first. Redirect to customer acquisition. |
| 🟩 **Launch-blocker UX/quality fix on shipped surface** | "FAB primer eats 5% of screen and won't dismiss", "Login button doesn't work on Safari", "Error toast covers Save button", "Existing flow looks autogenerated and unprofessional", "Modal traps focus", "Form silently drops on submit" | **NOT GATED.** Ship the fix. You cannot launch a hostile app. |

## The launch-blocker test

For any fix on an existing shipped surface, ask:

> *Would a real user, on first paid trial, see this and (a) abandon, (b) call the founder incompetent, or (c) ask for a refund?*

If yes → it is class 🟩 (launch-blocker). Ship it without the distribution-first caveat. The whole point of "launch first" is moot if "what gets launched" is incoherent or hostile.

If no → it may still be valid work, but apply the gate.

## What agents must NOT say

- ❌ "This is polish on a feature whose bottleneck is awareness, not [the symptom]" — when the symptom is a launch-blocker
- ❌ "Worth one mental tick before the next polish ticket" — when the fix is class 🟩
- ❌ "Build no launch — focus on distribution instead" — when the user is fixing existing hostile behavior, not adding new features
- ❌ Conflating "should we BUILD this thing that doesn't exist?" with "should we FIX this thing that already exists and is broken?"

## What agents should say instead

When a user requests a fix on an existing surface, classify first:

1. Is the request adding capability that doesn't exist today? → 🟥 new feature → apply gate
2. Is the request changing existing behavior, and would a paid user see this and abandon/refund/call-incompetent? → 🟩 launch-blocker → ship without gate
3. Otherwise → 🟨 polish → apply gate (with lighter weight; flag if uncertain)

When in doubt, lean toward shipping the fix. The framework's distribution-first principle exists to prevent endless feature-bloat that delays launch, not to prevent shipping a coherent, non-hostile product.

## Why this rule exists

Real failure mode observed 2026-05-06 on Example Marketplace: user requested fix to a Sample FAB whose primer card persisted and ate ~5% of mobile screen real estate on every customer visit. Agent diagnosed and shipped the fix correctly, but framed the work in closing notes as "30 minutes on UX polish for a feature whose bottleneck is awareness, not FAB-stack ergonomics — worth one mental tick before the next polish ticket." Implication: the user should have skipped the fix in favor of distribution work.

User correctly rebutted: *"I can't launch shit just because we say no new features. We want app to make at least some sense when users use it."*

The agent's framing was framework-misapplied. The fix was not new-feature scope creep — it was launch prerequisite work. The build-no-launch memory and rules treated the two as equivalent. They are not.

## Cross-project application

This rule supersedes any local project memory or feedback that gates "distribution-first" without distinguishing the three classes above. Project-specific memories MAY add additional class examples but MUST NOT remove the 🟩 carve-out.

## How a reviewer enforces this

`route-workflow`, `validate-feature`, and any skill that emits "distribution-first" / "build-no-launch" caveats must:

1. **Classify before caveating.** If the work is class 🟩 (launch-blocker on shipped surface), suppress the caveat entirely.
2. **Record the classification.** When a class 🟨 or 🟥 caveat IS emitted, the response should include a one-line classification ("class 🟨: feature polish") so the user can challenge the framing if wrong.
3. **Default to shipping when ambiguous.** If unclear whether a fix is 🟩 or 🟨, default to 🟩 and ship — the cost of shipping a small UX fix that wasn't strictly launch-blocking is trivial; the cost of redirecting to distribution while an existing surface is hostile is high.

`review-gate` should flag any session log where the agent applied build-no-launch / distribution-first language to a fix on existing shipped behavior. Severity: MEDIUM — pattern erodes user trust and stalls coherent product completion.

## Severity when violated

MEDIUM in a single occurrence (frame-and-correct). HIGH if the pattern recurs in the same project after this rule landed — at that point the agent is over-applying a framework principle in defiance of explicit user correction.
